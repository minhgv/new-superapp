## 1. `graded_throttle_fairness_and_mixed_client_requirements`

- **Source:** IETF RFC 5390 — Requirements for Management of Overload in the Session Initiation Protocol
- **Evidence level:** `official-informational-rfc-requirements`
- **Topic:** `runtime/overload-control/fairness/priority/retry-stability`
- **Detail:** [SOURCE STATUS] RFC 5390 is an Informational RFC, not a Standards Track protocol. [SOURCE FACT] REQ 4 says an overload mechanism must handle elements that do not support it and should improve incrementally as support grows; REQ 5 says it should resist malicious elements obtaining more than a fair share; REQ 7 requires graded throttling rather than an all-or-nothing response; REQ 8 says an overload/failure-rejected request must not be retried on an also-overloaded or unknown-status element; REQ 9 says rejection by an overloaded element must not unduly restrict submission to a non-overloaded element; REQ 13 leaves work prioritization to local policy; REQ 20 says non-participating elements must not receive disproportionate benefit; and REQ 21 calls for stability as offered load falls below capacity. [LIMITATION] These are SIP-specific requirements in an Informational RFC: they provide no mini-app identity model, quota units, weights, thresholds, retry token, or privacy/accessibility test method.

## 2. `fair_share_rate_caps_and_overload_stability`

- **Source:** IETF RFC 6357 — Design Considerations for Session Initiation Protocol (SIP) Overload Control
- **Evidence level:** `official-informational-rfc-design`
- **Topic:** `runtime/overload-control/fair-share/rate-caps/stability`
- **Detail:** [SOURCE STATUS] RFC 6357 is an Informational RFC describing SIP overload-control design considerations, not a normative mini-app scheduler. [SOURCE FACT] Its system model separates a control function that derives feedback/throttle from an actuator that enforces the throttle; the actuator can choose affected messages and reject or redirect them. It defines basic fairness as equal success chance for requests and customized fairness as priority/resource allocation such as an SLA. For rate-based control, each upstream neighbor can get a distinct cap, the sum should not substantially exceed actual capacity, and caps must be adjusted when neighbors join or leave; too-high caps can overload while too-low caps reject work that could have been processed. It lists goodput, delay, responsiveness, stability/no oscillation, fairness, self-limiting, changing neighbor sets, and computational overhead as evaluation dimensions. [MINI-APP STORE PROPOSAL] Treat app/publisher/tenant/operation as scheduler principals, allocate weighted or equal per-principal rate caps with explicit SLA/priority exceptions, recompute shares on active-principal changes, and choose reject/redirect/buffer only after checking alternate capacity and operation idempotency. Set the aggregate cap below measured safe capacity; publish default fairness versus exception rules; alert on cap oversubscription, underutilization, starvation, delay, and oscillation. [LIMITATION] RFC 6357 is a SIP design framework, not a normative mini-app scheduler; it does not define weights, admission tokens, tenant identity, cost accounting, or safe buffering/redirect semantics for web APIs.

## 3. `negotiated_overload_state_self_limiting_and_legacy_fairness`

- **Source:** IETF RFC 7339 — Session Initiation Protocol (SIP) Overload Control
- **Evidence level:** `official-standards-track-rfc`
- **Topic:** `runtime/overload-control/negotiation/self-limiting/non-participating-clients`
- **Detail:** [SOURCE STATUS] RFC 7339 is an Internet Standards Track specification for SIP overload control; its described SIP entities are assumed to support the specification unless stated otherwise. [SOURCE FACT] A SIP client MUST honor downstream overload values and MUST NOT forward more than allowed for that downstream server; control is hop-by-hop and scoped to a unique IP/port combination. Stored values expire and reset, and a server ends control by setting oc-validity=0 and incrementing oc-seq. Algorithm selection SHOULD remain unchanged for at least 3600 seconds so it can stabilize. After repeated timeouts or fatal transport errors, the client MUST stop sending, SHOULD probe conservatively such as with exponential backoff, and can resume after a normal response. A client may redirect only to a destination that is not overloaded and can take the extra load; otherwise it may buffer or reject with 503 without Retry-After. For a non-participating client, an overloaded server MUST reject some requests with 503 without Retry-After so nonparticipants do not gain an unfair advantage. [MINI-APP STORE PROPOSAL] Have the host negotiate and persist per-route runtime state: supported algorithm, current cap/reduction, validity, monotonic sequence, and effective principal/operation scope. Require SDKs to honor hard caps, expire stale state, fail closed after repeated gateway timeouts with bounded health probes, and use only health-checked alternate routes; apply the same rejection budget to legacy/non-participating mini-apps at the gateway. Keep scheduler mode stable for at least a configured soak period and expose state transitions and audit reasons. [LIMITATION] RFC 7339's hop-by-hop SIP/Via model is not an HTTP quota or billing model; it does not define per-user fairness weights, persistent queues, idempotency, or how to authenticate overload signals across a mini-app host boundary.

## 4. `rate_based_upper_bound_priority_lanes_and_burst_stability`

- **Source:** IETF RFC 7415 — Session Initiation Protocol (SIP) Rate Control
- **Evidence level:** `official-standards-track-rfc`
- **Topic:** `runtime/overload-control/rate-governance/priority/burst-stability`
- **Detail:** [SOURCE STATUS] RFC 7415 is an Internet Standards Track document and defines an optional rate-based SIP overload scheme under RFC 7339. [SOURCE FACT] It says a loss-based scheme cannot guarantee an upper bound and frequent updates may affect stability; the rate-based scheme guarantees an upper bound that is constant between server updates. The server MUST periodically evaluate overload and estimate a target rate and may allocate the same or different rate per client; the client algorithm must keep long-term rate below 1/T, with optional short bursts. With two thresholds TAU1<TAU2, all requests are admitted at or below TAU1, only higher-priority requests between the thresholds, and all requests are rejected at or above TAU2; this generalizes to n priorities. The RFC warns synchronized bucket occupancy can cause resonance, instability, poor delay, or loss and describes randomization to avoid it. [MINI-APP STORE PROPOSAL] Give each app/publisher/tenant/operation lane an explicit rate ceiling and token or leaky-bucket state over the whole request stream, not just low-priority calls; implement reserved high-priority lanes with bounded thresholds and a low-priority floor or aging rule to prevent starvation; add randomized refill or admission jitter for synchronized launches, while measuring long-term rate, burst size, queue age, and rejection by priority. Treat zero-rate state as an explicit stop condition and validity expiry as an explicit resume condition; only automatically retry operations that are idempotent or deduplicated. [LIMITATION] The RFC leaves target-rate allocation, threshold/tolerance values, communication between servers, and client priority policy out of scope; it is SIP-specific and does not itself define tenant fairness, costs, or safe retry semantics.

## Consolidated standard implications

1. **Use graded, fair-share admission rather than binary overload behavior.** Assign explicit scheduler principals (app, publisher, tenant, operation class and provider), expose versioned throttle state and fairness scope, and measure goodput, queue age, starvation, rejection, retry amplification, oscillation and underutilization. Keep control, entitlement, security and accessibility-critical operations in reserved but bounded lanes; do not let a non-participating or legacy client gain disproportionate capacity.
2. **Separate admission, queueing, retry and redirection.** A queued request still consumes capacity and a retry may duplicate side effects. Redirect only to a health-checked destination with spare capacity and an idempotent/deduplicated operation; otherwise reject or shed optional work with a deterministic error. Keep algorithm state, validity, sequence and expiry explicit.
3. **Make storage a declared resource, not an invisible browser side effect.** The mini-app manifest should declare partition identity, bucket class, approximate maximum bytes, reconstructible versus user-only data, eviction priority, persistence class and power-loss durability hint. The host should expose approximate usage, reclaim order, last eviction and an app-scoped clear operation while disclaiming that persistent/strict hints are not backups or universal byte guarantees.
4. **Preserve consistency across quota failure and eviction.** Use transaction or generation boundaries so package metadata, cache indexes and active-release pointers cannot partially commit. Keep rebuildable blobs separate from user-created state; on quota pressure retain the last-known-good state and return a recoverable, typed quota error.
5. **Apply operation-specific, privacy-aware abuse controls.** Maintain a versioned risk registry for discovery, account mutations, reservations, rewards, notifications, payments and provider-backed jobs. Combine authenticated principal/app/publisher/tenant partitions with network/device/session signals, but do not make one IP, forwarded header, device score or challenge failure an irreversible proof of abuse. Provide accessible friction alternatives, recovery and appeal, and measure false positives across shared-device/NAT, assistive-technology and low-connectivity cohorts.
6. **Distinguish alerts from hard spend enforcement.** Before dispatching a cost-bearing operation, authorize against an app/publisher/tenant/provider reserve or quota and persist the policy decision. Provider alerts and forecasts are not caps; use provider-side enforcement as a second boundary where available and reconcile delayed or uncertain charges. Carry host-generated operation IDs and payload fingerprints through provider adapters; same-key/different-payload and post-expiry ambiguity must not be silently retried.

## Remaining validation gaps

- SIP overload-control RFCs are useful algorithmic precedents but do not define HTTP mini-app quota units, identity, billing, privacy, accessibility, or thresholds.
- WHATWG/W3C storage specifications do not provide a universal native-host byte budget or cross-runtime eviction contract; WindVane/uni-app cache behavior must be measured on supported Android/iOS/Flutter versions.
- Provider idempotency, spend-cap and WAF partition semantics are implementation-specific; adapter contracts and reconciliation windows require Finance, Security and Platform-owner sign-off.
- Adaptive friction and abuse detection need calibrated fixtures with shared NAT/device, accessibility, legitimate bursts, offline retries, provider timeout, appeal and false-positive outcomes.
