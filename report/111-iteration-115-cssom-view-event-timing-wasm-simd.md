# 111. Iteration 115: W3C CSSOM View Visual Hit-Testing & Coordinate Sandboxing, W3C Event Timing API & INP Responsiveness Forensics, and WebAssembly Fixed-Width SIMD Vectorization & Linear Memory Concurrency Sandboxing

## Tổng quan và Bối cảnh Kiến trúc
Milestone 115 tập trung chuẩn hóa 3 trụ cột kỹ thuật tối quan trọng trong hạ tầng container super-app đa nhiệm hiện đại:
1. **W3C CSSOM View Visual Hit-Testing & Coordinate Sandboxing:** Chuẩn hóa mô hình hình học layout viewport vs visual viewport, cơ chế hit-testing điểm chạm qua `Document.elementFromPoint(x, y)` nhằm phát hiện và vô hiệu hóa các lớp phủ clickjacking tàng hình, phương thức `Document.elementsFromPoint(x, y)` duyệt toàn bộ ngăn xếp z-stack để kiểm toán các lớp giao diện lừa đảo, `Document.caretPositionFromPoint(x, y)` định vị con trỏ typographic chính xác cho bàn phím ảo và bộ gõ IME, cùng cơ chế đồng bộ tọa độ tuyệt đối qua `VisualViewport.pageLeft/pageTop` chống trôi lệch UI khi phóng to.
2. **W3C Event Timing API & Interaction to Next Paint (INP) Forensics:** Chuẩn hóa mô hình dữ liệu đo lường độ trễ tương tác người dùng qua `PerformanceEventTiming`, bóc tách định lượng 3 pha độ trễ quan trọng (Input Delay qua `processingStart - startTime`, Event Processing qua `processingEnd - processingStart`, và Presentation Delay), cơ chế gom cụm cử chỉ qua `interactionId` làm cơ sở tính toán Core Web Vitals INP (ngưỡng chuẩn hóa <= 200ms), áp dụng kiểm thử tự động phê duyệt mini-app marketplace.
3. **WebAssembly Fixed-Width SIMD Vectorization & Linear Memory Concurrency Sandboxing:** Chuẩn hóa tập lệnh véc-tơ 128-bit cố định (Wasm SIMD) trong W3C WebAssembly Core 2.0 cho các tác vụ tính toán song song hiệu năng cao (AI on-device, DSP âm thanh, xử lý đồ họa vector), quản trị an toàn bộ nhớ tuyến tính `WebAssembly.Memory` với cơ chế phân bổ trang 64KiB và giới hạn trần dung lượng, xử lý biến động tách rời bộ đệm (`buffer detachment`) khi gọi `Memory.prototype.grow()`, và bảo đảm an toàn đa luồng `SharedArrayBuffer` dưới ranh giới cô lập nguồn gốc Cross-Origin Isolation (COOP/COEP).

### 1. [STANDARDS-W3C-CSSOM-VIEW-COORDINATE-GEOMETRY-MODELS] W3C CSSOM View Module Level 1: Viewport Geometry, Scroll Offsets, and Coordinate Space Sandboxing
- **Danh mục:** `runtime-environment-and-mobile-layout-standards`
- **Mức độ bằng chứng:** `official_standard`
- **Tiêu chuẩn / Tài liệu kiểm chứng:** [https://www.w3.org/TR/cssom-view-1/](https://www.w3.org/TR/cssom-view-1/)
- **Mô tả kỹ thuật:** Details the normative specifications of W3C CSSOM View Module Level 1. Analyzes layout viewport vs visual viewport coordinate spaces, window geometry, and scroll boundaries in super-app webviews.
- **Phân tích chuẩn hóa chi tiết:** The W3C CSSOM View Module Level 1 Recommendation establishes the foundational mathematical geometry and programmatic APIs for inspecting and manipulating element layout and viewport dimensions in web runtimes. The specification distinguishes between the 'layout viewport' (the initial containing block against which CSS percentages and fixed positioning resolve) and the 'visual viewport' (the physical screen portion currently visible to the end user under pinch-to-zoom magnification and virtual keyboard emergence). In super-app webview containers, CSSOM View geometry APIs (window.innerWidth, window.innerHeight, screen.width, Element.getBoundingClientRect()) establish the coordinate reference frame. Container sandboxing mandates that sub-window framing and embedded third-party widgets cannot forge screen dimensions to escape containing boundaries or spoof system UI dialogs, ensuring predictable touch event routing across multi-window host layouts.

### 2. [STANDARDS-CSSOM-DOCUMENT-ELEMENTFROMPOINT-HIT-TESTING] Document.elementFromPoint: Compositor Hit-Testing, Topmost Element Resolution, and Clickjacking Sandboxing

- **Mô tả kỹ thuật:** Examines the Document.elementFromPoint(x, y) method in CSSOM View, covering client coordinate hit-testing, pointer-events: none pass-through, and defenses against clickjacking overlay attacks.
- **Phân tích chuẩn hóa chi tiết:** The Document.elementFromPoint(x, y) method returns the topmost Element object located at the specified viewport client coordinates (x, y) relative to the top-left of the visual viewport. If the specified point falls outside the visible document viewport or targets an element styled with 'pointer-events: none', the method returns null or descends to the underlying interactive element. In super-app security architecture, elementFromPoint serves as an essential runtime verification tool: security sandboxes and host review harnesses programmatically sample coordinate points across payment buttons, permission grant dialogs, and embedded webviews to confirm that malicious third-party mini-apps have not deployed invisible opacity=0 clickjacking overlays or rogue iframe veils over critical platform controls.

- **Mô tả kỹ thuật:** Details the Document.elementsFromPoint(x, y) method in CSSOM View, analyzing full visual stack introspection, shadow root traversal, and automated detection of deceptive UI layers.
- **Phân tích chuẩn hóa chi tiết:** The Document.elementsFromPoint(x, y) method returns an ordered array of all Element objects intersecting the designated client coordinates, sequenced in descending z-order from the topmost visual element down to the root <html> container. Unlike elementFromPoint which only identifies the surface target, elementsFromPoint traverses the entire rendering stacking context hierarchy, revealing elements concealed beneath semi-transparent backdrops or overlapping positioned layers. Super-app automated quality gates and security runtime monitors execute elementsFromPoint during dynamic mini-app scanning to detect deceptive visual stacking patterns—such as transparent touch interceptors layered atop simulated native login inputs—ensuring complete transparency and provenance across all interactive surface coordinates.

- **Mô tả kỹ thuật:** Analyzes the processingEnd attribute in PerformanceEventTiming, examining processing duration vs presentation delay (duration - (processingEnd - startTime)) to optimize next-frame rendering budgets.

In mobile mini-app containers, high presentation delay points directly to DOM thrashing, deep component tree mutations, or expensive CSS layout calculations triggered inside event handlers. Super-app UI best practices require mini-apps to defer heavy DOM mutations until after transient feedback animations render, ensuring immediate visual acknowledgment within a single 16.6ms / 60 FPS display frame.

### 13. [STANDARDS-WASM-MEMORY-GROW-BUFFER-DETACHMENT-AND-OOM-HANDLING] WebAssembly.Memory.prototype.grow: Dynamic Linear Memory Expansion, Buffer Detachment, and OOM Resilience
- **Danh mục:** `runtime-environment-and-wasm-sandboxing`
- **Mức độ bằng chứng:** `official_standard`
- **Tiêu chuẩn / Tài liệu kiểm chứng:** [https://developer.mozilla.org/en-US/docs/WebAssembly/JavaScript_interface/Memory/grow](https://developer.mozilla.org/en-US/docs/WebAssembly/JavaScript_interface/Memory/grow)
- **Mô tả kỹ thuật:** Details the Memory.prototype.grow() method in the WebAssembly JavaScript interface, analyzing page increment mechanics, ArrayBuffer detachment, and memory growth failure error handling.
- **Phân tích chuẩn hóa chi tiết:** The WebAssembly.Memory.prototype.grow(delta) method dynamically increases the linear memory allocation by a specified number of 64KiB pages, returning the previous page count or throwing a RangeError if the growth exceeds the declared maximum or system capacity. A critical architectural consequence of grow() in non-shared memories is that the underlying JavaScript ArrayBuffer instance is immediately detached (byteLength becomes 0) and replaced with a newly allocated buffer. Mini-app JavaScript glue code (e.g., Emscripten / wasm-bindgen) and host bridge adapters must not hold persistent references to memory.buffer TypedArrays across potential allocation boundaries. Super-app runtime wrappers intercept grow calls to log memory consumption telemetry and prevent memory fragmentation crashes under low-RAM mobile conditions.
