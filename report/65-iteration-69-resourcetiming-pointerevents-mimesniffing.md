# Chuyên đề 65: W3C Resource Timing Level 2, W3C Pointer Events Level 3 & WHATWG MIME Sniffing / nosniff

## 1. Tổng quan Nghiên cứu & Định vị Chuẩn (Milestone 69)

Trong khuôn khổ Milestone 69, nghiên cứu tập trung vào 3 trụ cột kỹ thuật trọng yếu của web platform hiện đại, bảo đảm tính minh bạch hiệu năng mạng, độ chính xác tương tác phần cứng và an ninh thực thi tài nguyên mã nguồn:

1. **W3C Resource Timing Level 2 & Server-Timing Telemetry**: Thiết lập chuẩn mực đo lường chi tiết vòng đời tải tài nguyên mạng (DNS, TCP, TLS, TTFB, Body Download) qua giao diện `PerformanceResourceTiming`, phân tách độ trễ khởi động Service Worker qua `workerStart`, thiết lập ranh giới an toàn chống rò rỉ kênh phụ XS-Leaks qua HTTP header `Timing-Allow-Origin` (TAO), và đồng bộ hóa các span truy vết vi dịch vụ backend thông qua chuẩn `Server-Timing` kết hợp W3C Trace Context.
2. **W3C Pointer Events Level 3 & Multi-Modal Input Sandboxing**: Thống nhất mô hình tương tác phần cứng (chuột, bút cảm ứng stylus, màn hình cảm ứng đa điểm multi-touch) thành một giao diện sự kiện `PointerEvent` đồng nhất. Hỗ trợ đầy đủ dữ liệu đo lường vật lý (áp lực pressure, góc nghiêng tiltX/tiltY, góc quay twist, altitude/azimuth) phục vụ chữ ký số sinh trắc học e-Signatures; khai thác `getCoalescedEvents()` để tái tạo nét vẽ mượt mà ở tần số lấy mẫu phần cứng 240Hz; ứng dụng `getPredictedEvents()` nhằm triệt tiêu độ trễ hiển thị dưới 8ms; và cô lập vùng kéo thả an toàn qua `setPointerCapture()`.
3. **WHATWG MIME Sniffing Standard & X-Content-Type-Options: nosniff Governance**: Chuẩn hóa thuật toán phân tích mẫu byte nhận diện định dạng tệp tin, loại bỏ các heuristic đoán định dạng nguy hiểm từ lịch sử trình duyệt. Thực thi nghiêm ngặt HTTP header `X-Content-Type-Options: nosniff` nhằm từ chối thực thi các script và stylesheet bị gắn nhãn sai lệch; áp dụng cơ chế xác thực MIME theo ngữ cảnh đích của WHATWG Fetch kết hợp CORB/ORB; bắt buộc kiểu MIME JavaScript chuẩn xác đối với ECMAScript Modules; và kiểm soát tính toàn vẹn biên dịch luồng WebAssembly thông qua nhãn `application/wasm`.

### resource_timing_069_01: W3C Resource Timing Level 2 & Detailed Subresource Waterfall Telemetry

- **Chủ đề**: `resource_timing_l2_network_telemetry` | **Nhóm chuyên mục**: `Operational Reliability, SRE, Recovery & Observability`
- **Mức bằng chứng**: `specification` | **Chuẩn tham chiếu**: W3C Resource Timing Level 2 §4 PerformanceResourceTiming Interface
- **URL Chuẩn**: [https://www.w3.org/TR/resource-timing-2/](https://www.w3.org/TR/resource-timing-2/)
- **Nguồn hỗ trợ / Triển khai**: [https://developer.mozilla.org/en-US/docs/Web/API/PerformanceResourceTiming](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceResourceTiming), [https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Timing-Allow-Origin](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Timing-Allow-Origin)
- **Tóm tắt cốt lõi**: Resource Timing Level 2 exposes high-precision phase breakdowns of subresource network requests, establishing granular observability for mini-app packaging, bundle loading, and API latency.
- **Phân tích kỹ thuật chuyên sâu & Kiến trúc Super-App**:
  [SPEC FACT] The W3C Resource Timing Level 2 specification extends PerformanceEntry to define 'PerformanceResourceTiming', capturing microsecond-resolution DOMHighResTimeStamp milestones for every resource fetched by the user agent. The metric pipeline decomposes network requests into deterministic lifecycle phases: redirectStart/redirectEnd, workerStart (Service Worker boot latency), domainLookupStart/domainLookupEnd (DNS resolution), connectStart/connectEnd (TCP three-way handshake), secureConnectionStart (TLS cryptographic negotiation), requestStart, responseStart (Time To First Byte / TTFB), and responseEnd (body download completion). Additionally, transferSize, encodedBodySize, and decodedBodySize quantify HTTP compression ratios and network cache hits (transferSize == 0). [SUPERAPP ARCHITECTURE] Super-app mini-apps pull heterogeneous assets across CDNs, host gateways, and partner microservices. By attaching a PerformanceObserver with type 'resource' and buffered=true, the host container captures network waterfall diagnostics across all child mini-app frames. Slow network phases (such as excessive DNS lookups or bloated TLS handshakes across unbundled third-party origins) are flagged during store review and runtime telemetry, enforcing strict subresource budget limits (total mini-app payload transferSize <= 4MB, responseStart <= 600ms on 4G networks).

- **Phân tích kỹ thuật chuyên sâu & Kiến trúc Super-App**:

[SUPERAPP ARCHITECTURE] In enterprise super-app architectures, mini-app API calls route through a multi-tenant API gateway before reaching backend banking, telco, or merchant backends. The gateway injects standardized Server-Timing metrics into upstream API responses. The super-app client SDK aggregates serverTiming arrays and bundles them with client-side PerformanceResourceTiming metrics into telemetry payloads. This bridges frontend latency regressions directly to backend database deadlocks or microservice cold-starts without requiring intrusive server log correlation.

- **Chủ đề**: `timing_allow_origin_security_boundary` | **Nhóm chuyên mục**: `Operational Reliability, SRE, Recovery & Observability`
- **Mức bằng chứng**: `specification` | **Chuẩn tham chiếu**: W3C Resource Timing Level 2 §5 Cross-origin data protection & Timing-Allow-Origin
- **URL Chuẩn**: [https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Timing-Allow-Origin](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Timing-Allow-Origin)
- **Nguồn hỗ trợ / Triển khai**: [https://www.w3.org/TR/resource-timing-2/](https://www.w3.org/TR/resource-timing-2/), [https://developer.mozilla.org/en-US/docs/Web/API/PerformanceResourceTiming](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceResourceTiming)
- **Tóm tắt cốt lõi**: Timing-Allow-Origin controls cross-origin exposure of detailed network timing attributes, preventing XS-Leaks and timing side-channel attacks against third-party endpoints.
- **Phân tích kỹ thuật chuyên sâu & Kiến trúc Super-App**:
  [SPEC FACT] To protect user privacy and prevent timing side-channel attacks (Cross-Site Search / XS-Leaks), user agents zero out detailed timing attributes (redirectStart/End, domainLookupStart/End, connectStart/End, secureConnectionStart, requestStart, responseStart) for cross-origin resources, setting them identical to startTime/responseEnd unless the server explicitly grants access via the 'Timing-Allow-Origin' (TAO) HTTP header. The header accepts a wildcard ('Timing-Allow-Origin: *') or specific origins ('Timing-Allow-Origin: https://miniapp.superapp.vn'). Without a valid TAO header, cross-origin subresources only reveal overall duration and transferSize=0, preventing malicious scripts from probing intranet resources or inferring user authentication state via network latency variations. [SUPERAPP ARCHITECTURE] Super-app mini-apps frequently consume resources hosted across partner CDNs, analytics providers, and third-party payment gateways. The super-app standard mandates that partner CDNs serving mini-app subresources must explicitly supply 'Timing-Allow-Origin: https://<superapp-domain>' or wildcard '*' for public immutable assets. Simultaneously, sensitive authenticated APIs (such as payment authorization endpoints) must strictly omit TAO or restrict it to authenticated host origins, ensuring timing side-channel safety while preserving full performance observability for core mini-app infrastructure.

The host container polyfills or normalizes native touch gestures into standard PointerEvents, enforcing predictable input handling across Android, iOS, and desktop webviews.

### pointer_events_069_03: getCoalescedEvents() & Sub-Frame High-Fidelity Stroke Reconstruction

- **Chủ đề**: `pointer_event_coalesced_events_subframe_fidelity` | **Nhóm chuyên mục**: `Interoperability, Manifest & Discovery`
- **Mức bằng chứng**: `specification` | **Chuẩn tham chiếu**: W3C Pointer Events Level 3 §5.2 getCoalescedEvents method
- **URL Chuẩn**: [https://developer.mozilla.org/en-US/docs/Web/API/PointerEvent/getCoalescedEvents](https://developer.mozilla.org/en-US/docs/Web/API/PointerEvent/getCoalescedEvents)
- **Nguồn hỗ trợ / Triển khai**: [https://www.w3.org/TR/pointerevents3/](https://www.w3.org/TR/pointerevents3/), [https://developer.mozilla.org/en-US/docs/Web/API/PointerEvent](https://developer.mozilla.org/en-US/docs/Web/API/PointerEvent)
- **Tóm tắt cốt lõi**: getCoalescedEvents() grants access to all intermediate hardware touch/pen coordinate points merged by the browser event loop during a single animation frame.
- **Phân tích kỹ thuật chuyên sâu & Kiến trúc Super-App**:
  [SPEC FACT] Modern touchscreens and digitizers sample input at 120Hz to 240Hz, whereas the browser main thread and screen compositor typically render at 60Hz or 120Hz. To avoid event loop congestion, user agents coalesce multiple intermediate hardware touch samples into a single dispatch of 'pointermove'. The 'getCoalescedEvents()' method returns a sequence of PointerEvent objects representing all un-coalesced raw hardware events that occurred since the previous dispatch. Each coalesced event retains its unique high-precision timestamp, precise fractional coordinates, and instantaneous pressure values. [SUPERAPP ARCHITECTURE] When mini-app users draw rapid curves or write signatures on a canvas, drawing solely from the dispatched pointermove event produces jagged, polygonal strokes due to missed intermediate points. By invoking e.getCoalescedEvents(), mini-app drawing engines reconstruct the full 240Hz trajectory, delivering silky-smooth stroke interpolation and accurate velocity curves. Store quality gates verify that e-signature and drawing mini-apps consume getCoalescedEvents() to prevent broken or degraded signature capture on high-refresh-rate mobile devices.

### pointer_events_069_04: getPredictedEvents() & Algorithmic Low-Latency Stroke Prediction

- **Chủ đề**: `pointer_event_predicted_events_latency_reduction` | **Nhóm chuyên mục**: `Interoperability, Manifest & Discovery`
- **Mức bằng chứng**: `specification` | **Chuẩn tham chiếu**: W3C Pointer Events Level 3 §5.3 getPredictedEvents method
- **URL Chuẩn**: [https://developer.mozilla.org/en-US/docs/Web/API/PointerEvent/getPredictedEvents](https://developer.mozilla.org/en-US/docs/Web/API/PointerEvent/getPredictedEvents)
- **Nguồn hỗ trợ / Triển khai**: [https://www.w3.org/TR/pointerevents3/](https://www.w3.org/TR/pointerevents3/), [https://developer.mozilla.org/en-US/docs/Web/API/PointerEvent](https://developer.mozilla.org/en-US/docs/Web/API/PointerEvent)
- **Tóm tắt cốt lõi**: getPredictedEvents() provides speculative future pointer positions calculated by the browser's hardware Kalman filter, eliminating visible stylus tracking latency.
- **Phân tích kỹ thuật chuyên sâu & Kiến trúc Super-App**:
  [SPEC FACT] Due to display scanout time and hardware processing pipelines, drawing on a digital touchscreen exhibits physical latency (typically 15ms to 35ms between the physical pen tip and the drawn ink line). The 'getPredictedEvents()' method returns a sequence of synthetic PointerEvent objects generated by the user agent's predictive motion algorithms (such as Kalman filters or polynomial regression based on recent velocity and acceleration). These predicted points indicate where the pointer is expected to be by the time the next display frame finishes scanning out. Applications draw speculative ink to predicted coordinates, discarding and replacing them once authoritative hardware events arrive in subsequent frames. [SUPERAPP ARCHITECTURE] Super-app mini-apps competing with native mobile apps often suffer from perception of 'web lag' during stylus annotation or document markup. The super-app standard provides a hardware-accelerated canvas utility component that automatically leverages getPredictedEvents(). By speculatively extending ink trails to the pen tip, perceived drawing latency is reduced from ~30ms to under 8ms, matching native iOS PencilKit and Android S-Pen responsiveness.

[SUPERAPP ARCHITECTURE] Mini-app UI components (such as custom sliders, range pickers, audio scrubbers, and bottom sheet drag handles) frequently fail or glitch when a fast touch drag strays beyond the component's bounding box. Without pointer capture, events leak to parent scroll containers or host navigation bars. The super-app UI component framework mandates setPointerCapture() on pointerdown for all drag-and-drop and scrubbing controls. Furthermore, listeners on 'lostpointercapture' guarantee state reconciliation and prevent stuck drag states if the host super-app displays a security modal.

### mime_sniffing_069_01: WHATWG MIME Sniffing Standard & Content-Type Ambiguity Defense

- **Chủ đề**: `whatwg_mime_sniffing_standard_algorithms` | **Nhóm chuyên mục**: `Security, Supply Chain & Device Boundaries`
- **Mức bằng chứng**: `specification` | **Chuẩn tham chiếu**: WHATWG MIME Sniffing Standard §4 Matching a MIME type pattern
- **URL Chuẩn**: [https://mimesniff.spec.whatwg.org/](https://mimesniff.spec.whatwg.org/)
- **Nguồn hỗ trợ / Triển khai**: [https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/X-Content-Type-Options](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/X-Content-Type-Options), [https://fetch.spec.whatwg.org/](https://fetch.spec.whatwg.org/)
- **Tóm tắt cốt lõi**: The WHATWG MIME Sniffing Standard specifies deterministic byte pattern matching algorithms to eliminate legacy browser heuristics that cause cross-site script execution.
- **Phân tích kỹ thuật chuyên sâu & Kiến trúc Super-App**:
  [SPEC FACT] Legacy web browsers historically examined resource byte prefixes (magic numbers) to guess MIME types when the HTTP 'Content-Type' header was missing, generic (application/octet-stream), or incorrect. The WHATWG MIME Sniffing standard formalizes precise algorithms for image, audio/video, font, and text sniffing, defining exact byte masks for formats like GIF87a/89a, PNG, JPEG, and WebP. Importantly, section 6 dictates that when an HTTP response contains an invalid or text/plain header, browsers must not sniff HTML tags (<html, <script) if the context requires safety. Exploiting loose sniffing, attackers upload malicious polyglot images containing embedded HTML/JavaScript to image hosting endpoints, tricking browsers into executing them as script. [SUPERAPP ARCHITECTURE] Super-app mini-apps allow user-generated content (UGC), avatar uploads, and dynamic document downloads. If the super-app container or mini-app asset CDN relies on ambient MIME sniffing, polyglot files can execute within the mini-app origin, compromising authentication tokens and private storage. The super-app standard mandates that all container asset loaders, local package proxies, and CDN edge endpoints implement WHATWG MIME sniffing validation and strip ambiguous Content-Type declarations before asset injection.

### mime_sniffing_069_02: X-Content-Type-Options: nosniff & Strict Execution MIME Gating

- **Chủ đề**: `x_content_type_options_nosniff_header` | **Nhóm chuyên mục**: `Security, Supply Chain & Device Boundaries`
- **Mức bằng chứng**: `specification` | **Chuẩn tham chiếu**: WHATWG Fetch Standard §3.2.1 Corb & X-Content-Type-Options: nosniff
- **URL Chuẩn**: [https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/X-Content-Type-Options](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/X-Content-Type-Options)
- **Nguồn hỗ trợ / Triển khai**: [https://mimesniff.spec.whatwg.org/](https://mimesniff.spec.whatwg.org/), [https://fetch.spec.whatwg.org/](https://fetch.spec.whatwg.org/)
- **Tóm tắt cốt lõi**: X-Content-Type-Options: nosniff instructs the user agent to strictly enforce declared MIME types, aborting execution of mislabeled scripts and stylesheets.
- **Phân tích kỹ thuật chuyên sâu & Kiến trúc Super-App**:
  [SPEC FACT] The 'X-Content-Type-Options: nosniff' HTTP response header disables the browser's MIME type sniffing algorithms. Under 'nosniff', the browser enforces two strict security barriers: (1) Scripts (<script src>) are rejected and will not execute unless their declared Content-Type header matches a valid JavaScript MIME type ('application/javascript', 'text/javascript', 'application/ecmascript', etc.); (2) Stylesheets (<link rel="stylesheet">) are rejected unless served with 'text/css'. If an attacker uploads a JavaScript payload masquerading as an image (image/png) or plain text (text/plain), 'nosniff' causes the fetch to fail with a network error, completely neutralizing MIME-confusion XSS attacks. [SUPERAPP ARCHITECTURE] Super-app mini-app packages consist of HTML, JS bundles, CSS stylesheets, and static media served via internal package protocols (e.g., miniapp-package:// or localhost webview proxies). The super-app host container mandates that internal protocol handlers and edge CDN servers append 'X-Content-Type-Options: nosniff' to every single response. Store review automated scanners inspect packaged headers and fail any mini-app that attempts to bypass nosniff, ensuring robust defense against script smuggling.

- **Tóm tắt cốt lõi**: WHATWG Fetch mandates destination-aware MIME validation across request contexts (script, style, worker, audio, video), preventing cross-origin data theft.
- **Phân tích kỹ thuật chuyên sâu & Kiến trúc Super-App**:
  [SPEC FACT] The WHATWG Fetch Standard defines strict response validation based on 'request.destination'. When destination is 'script' or 'worker', the response's extract-a-MIME-type algorithm must yield a JavaScript MIME type if nosniff is set, and must not match audio/video/image types. [SUPERAPP ARCHITECTURE] Super-app mini-apps operate in a sandboxed webview where third-party libraries might attempt unauthorized cross-origin requests. The super-app runtime intercepts fetch() calls at the bridge layer, enforcing destination-specific MIME validation and validating that API responses returning sensitive customer JSON data are never fetchable via <script src> tags. This guarantees that multi-tenant mini-apps cannot exploit cross-origin read leaks against banking or telco backend APIs.

Store submission pipelines verify that mini-app code relies on strict ES Module loading, eliminating obsolete classic script behaviors and closing legacy CORS-bypass vectors.

## 4. Hướng dẫn Tích hợp & Kiểm toán Cửa hàng Mini App (Store Review Criteria)

1. **Kiểm toán Đo lường Tài nguyên Mạng (Resource Timing & Server-Timing)**:
   - Mọi mini app khi phát hành phải bảo đảm tổng thời gian nạp subresource không vượt quá ngân sách mạng (Total Transfer Size <= 4MB, TTFB <= 600ms trên mạng di động 4G).
   - Các CDN lưu trữ tài nguyên tĩnh dùng chung phải cấu hình `Timing-Allow-Origin: *` hoặc chỉ định chính xác domain của Super-App nhằm cho phép SDK giám sát waterfall phân tích chi tiết các giai đoạn DNS/TCP/TLS.
   - Cổng API Gateway vi dịch vụ của Super-App bắt buộc chèn header `Server-Timing` gắn mã traceparent của W3C Trace Context và tước bỏ các tham số mô tả nhạy cảm (như raw SQL query hoặc internal microservice IP) trước khi chuyển tiếp cho Webview.
2. **Kiểm toán Giao diện Tương tác Phần cứng (Pointer Events Level 3)**:
   - Cấm sử dụng các sự kiện chuột truyền thống (MouseEvent) và sự kiện cảm ứng riêng biệt (TouchEvent) độc lập gây ra hiện tượng 300ms click delay hoặc double-fire; toàn bộ luồng tương tác cử chỉ phải chuẩn hóa qua `PointerEvent`.
   - Các mini app ký hợp đồng tài chính (leasing, bảo hiểm, e-banking) bắt buộc ứng dụng `e.getCoalescedEvents()` để thu thập toàn vẹn véc-tơ tọa độ và áp lực bút ở tần số 120-240Hz, đảm bảo giá trị pháp lý cho chữ ký số điện tử.
   - Các thành phần kéo thả (bottom sheet, thanh trượt slider, audio scrubber) bắt buộc đăng ký `setPointerCapture(pointerId)` trên sự kiện `pointerdown` và giải phóng an toàn khi nhận `lostpointercapture`.
3. **Kiểm toán An toàn Kiểu Tệp & Chống Rò rỉ Script (MIME Sniffing & nosniff)**:
   - Máy chủ nội bộ của Super-App và CDN phân phối gói mini app bắt buộc cấu hình tiêu đề HTTP `X-Content-Type-Options: nosniff` trên 100% các phản hồi HTTP.
   - Bộ kiểm tra bảo mật tự động tại cổng nộp bài (Store Ingestion Pipeline) quét toàn bộ tệp `.js`, `.mjs`, `.wasm`, `.css` và từ chối cấp phép nếu tệp được nạp với MIME generic `application/octet-stream` hoặc `text/plain`.
   - Mã nguồn WebAssembly phải được nạp thông qua `WebAssembly.compileStreaming` với kiểu nội dung chính xác là `application/wasm`, ngăn chặn triệt để tấn công tiêm mã nhị phân độc hại.
