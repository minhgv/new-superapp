# Chuyên đề 18: Chuẩn W3C MiniApp, Bảo mật Phân phối Gói TUF/SLSA/Sigstore và Quản trị Thiết bị Ngoại vi (Permissions Policy)

## 1. Bối cảnh và Mục tiêu Nghiên cứu Iteration 22

Iteration 22 tập trung chuẩn hóa kiến trúc cốt lõi của Mini App Store trên Super App dựa trên 3 trụ cột kỹ thuật chuẩn quốc tế:
1. **W3C MiniApp Working Group Standards**: Bộ tiêu chuẩn chính thức của W3C về Manifest, Packaging, Addressing, Lifecycle và Kiến trúc đa luồng (Dual-Thread Architecture) phân tách View và Logic Worker.
2. **TUF (The Update Framework), SLSA v1.0 & Sigstore**: Khung bảo đảm tính toàn vẹn chuỗi cung ứng phần mềm (Software Supply Chain Security), ngăn chặn tấn công rollback, freeze attack, compromised CDN edge, và chứng thực danh tính nhà phát triển không khóa (keyless signing với OIDC & Rekor transparency log).
3. **W3C Permissions Policy & Device Capabilities Governance**: Quản trị ủy quyền phần cứng và cảm biến thiết bị (Camera, Microphone, Geolocation, Web Bluetooth, Web NFC, Generic Sensors, Screen Wake Lock) qua mô hình chính sách phân lớp (Permissions Policy Envelope -> Host Consent Dialog -> Foreground Liveness Gate -> Revocation/Throttling).

Toàn bộ 16 phát hiện mới trong vòng nghiên cứu này đều được kiểm chứng độc lập với mã trạng thái HTTP 200 từ các nguồn chuẩn chính thức (W3C, IETF/TUF, SLSA, Sigstore, MDN).

## 3. Phân tích Chi tiết Từng Trụ cột Tiêu chuẩn

### 3.1. [manifest] MiniApp Manifest defines the store and runtime contract for identity, routes, permissions, icons, and window/theme configuration
- **Chuẩn tham chiếu**: W3C MiniApp Manifest — Conformance; pages, req_permissions, color_scheme, widgets, and window member-processing sections
- **Mức độ bằng chứng**: `normative_standard`
- **Nguồn kiểm chứng**: [https://w3c.github.io/miniapp-manifest/](https://w3c.github.io/miniapp-manifest/)
- **Nguồn bổ trợ**: [https://w3c.github.io/miniapp-packaging/](https://w3c.github.io/miniapp-packaging/), [https://w3c.github.io/miniapp-lifecycle/](https://w3c.github.io/miniapp-lifecycle/)
- **Chi tiết kỹ thuật**: The manifest is a JSON document that extends/profiles the Web App Manifest and Web App Manifest - Application Information. Its root MUST contain app_id, icons, name, pages, platform_version, and version; every icon resource MUST include src. The pages list contains relative page routes and its first item is the homepage/entry point. Optional req_permissions entries declare concrete system features such as location, contacts, sensors, or camera and may include a reason; the specification says user agents ask for consent and app stores/hosts may filter MiniApps using this data, privacy policy, user preferences, or device capabilities. Optional widgets use name/path entries. The optional window object covers navigation/title/background styles, fullscreen, pull-to-refresh, and orientation. color_scheme MUST be auto, light, or dark and overrides related window colors; theme_color, scope, and shortcuts are not currently supported by MiniApp user agents.
- **Khả năng áp dụng vào Super App**: Make manifest validation a submission gate: require stable app_id/version, verify every route and icon, derive the default launch page from pages[0], expose declared permissions and reasons in review and consent UX, filter eligibility by device/capability, and map window/orientation/color-scheme settings to host UI policy. Treat unsupported Web Manifest members as non-portable rather than silently assuming PWA behavior.

### 3.2. [packaging] MiniApp Packaging standardizes the ZIP artifact, reserved file layout, integrity hooks, and runtime processing while leaving split-package signing open
- **Chuẩn tham chiếu**: W3C MiniApp Packaging — Package Conformance; Directory and File System Structure; MiniApp ZIP Container; package processing and signature sections
- **Mức độ bằng chứng**: `normative_standard`
- **Nguồn kiểm chứng**: [https://w3c.github.io/miniapp-packaging/](https://w3c.github.io/miniapp-packaging/)
- **Nguồn bổ trợ**: [https://w3c.github.io/miniapp-manifest/](https://w3c.github.io/miniapp-manifest/), [https://w3c.github.io/miniapp-white-paper/](https://w3c.github.io/miniapp-white-paper/)
- **Chi tiết kỹ thuật**: A conformant package MUST use a root directory plus pages directory and MUST contain root manifest.json, app.js, app.css, with the whole package wrapped as a ZIP file. Page resources are matched by basename (HTML structure, CSS style, JavaScript logic) and routes are listed in the manifest; common and i18n directories are optional, with i18n filenames using BCP 47 language tags. ZIP containers MUST use UTF-8 filenames, CRC32 per-file integrity, and MUST NOT use ZIP encryption, split/spanned archives, or patented features; an optional signing block sits immediately before the central directory. Retrieval accepts the MIME type application/miniapp-pkg+zip, then the user agent retrieves, verifies, unzips, parses manifest.json, prepares the runtime, and selects the start page. The security guidance calls for a sandbox that blocks powerful features by default, CSP/resource restrictions, and discarding undeclared package resources. Package confidentiality encryption is not recommended by this specification. The RPK example defines a signing-block header with uint64/uint32 length fields, ID-value pairs, the magic string RPK Sig Block 42, and digest/certificate/signature sections. The document notes that distribution platforms may split a package into sub-packages, but additional signatures for each sub-package and the whole package are further study; the White Paper describes on-demand main/subpackage loading separately, not as core ZIP conformance.
- **Khả năng áp dụng vào Super App**: Treat the ZIP as the store supply-chain artifact: unpack and validate structure, MIME, routes, declared resources, and malware/CSP policy before publication; retain author and distributor signatures where supported; serve immutable package versions and verify integrity on download/cache; design subpackage manifests, per-subpackage digests/signatures, cache eviction, and progressive loading as explicit platform extensions because the base specification does not finish that contract.

### 3.3. [addressing_navigation] MiniApp Addressing defines deep-link syntax and host/provider resolution from OS dispatch to an in-package resource
- **Chuẩn tham chiếu**: W3C MiniApp Addressing — URI syntax, URI components, dereferencing, HTTPS package retrieval, and conformance sections
- **Mức độ bằng chứng**: `normative_standard`
- **Nguồn kiểm chứng**: [https://w3c.github.io/miniapp-addressing/](https://w3c.github.io/miniapp-addressing/)
- **Nguồn bổ trợ**: [https://w3c.github.io/miniapp-packaging/](https://w3c.github.io/miniapp-packaging/), [https://w3c.github.io/miniapp-manifest/](https://w3c.github.io/miniapp-manifest/)
- **Chi tiết kỹ thuật**: The ABNF is miniappuri = uri-prefix uri-infix "/" identify path-abempty ["?" query] ["#" fragment], with uri-prefix either a custom-scheme followed by :// or an HTTPS host path, uri-infix fixed to miniapp, and identify formed from mandatory id plus optional ;version=. The task shorthand miniapp:// is not the literal grammar: examples use forms such as platform://miniapp/foo/pages/index and https://platform.org/miniapp/foo/pages/index. id identifies a MiniApp under a package provider; id plus version selects a package, while an omitted version lets the user agent/provider choose a current/default/mapped version. The host is a logical namespace and is explicitly not the download location. OS dispatches by URI prefix, the user agent parses id/version/path/query/fragment, prefers a local package path before a remote package server, resolves the resource using path/query/fragment and Manifest rules, and MUST handle dereferencing failures. The HTTPS example requires HTTPS, returns errors for failed authentication/unsupported methods/not found, and recommends an integrity identifier plus package format from MiniApp Packaging; security guidance recommends anti-replay and package-integrity checks.
- **Khả năng áp dụng vào Super App**: Use one canonical deep-link resolver for QR codes, search results, catalog cards, push notifications, and cross-MiniApp navigation. Maintain an explicit provider/host-to-package-registry mapping, resolve id/version before path, keep path/query/fragment separate for routing and privacy, support offline local-cache precedence, and return actionable errors for missing/unauthorized/version-incompatible packages. Do not assume the host string is the CDN URL or collapse the custom-scheme and HTTPS forms into one unvalidated parser.

### 3.4. [lifecycle] MiniApp Lifecycle supplies global and page state machines with host callbacks for foregrounding, suspension, errors, rendering readiness, and unload
- **Chuẩn tham chiếu**: W3C MiniApp Lifecycle — Global Application Lifecycle and Page Lifecycle events, states, IDL interfaces, and security/privacy considerations
- **Mức độ bằng chứng**: `normative_standard`
- **Nguồn kiểm chứng**: [https://w3c.github.io/miniapp-lifecycle/](https://w3c.github.io/miniapp-lifecycle/)
- **Nguồn bổ trợ**: [https://w3c.github.io/miniapp-manifest/](https://w3c.github.io/miniapp-manifest/), [https://w3c.github.io/miniapp-white-paper/](https://w3c.github.io/miniapp-white-paper/)
- **Chi tiết kỹ thuật**: The global application states are launched, shown, hidden, error, and unloaded, exposed through GlobalState and ongloballaunched, onglobalshown, onglobalhidden, onglobalerror, and onglobalunloaded handlers. Closing or backgrounding does not immediately destroy the MiniApp; the user agent can later unload it after resource/time criteria. Page states are loaded, ready, shown, hidden, and unloaded, exposed through PageState and onpageloaded, onpageready, onpageshown, onpagehidden, and onpageunloaded handlers. The first-render sequence initializes View and Logic layers, establishes their communication channel, sends initial data from Logic to View, and marks page ready after the UI update. PageInputObject.pageInputQuery carries query parameters supplied by navigation/redirect APIs, and global input exposes page path/referrer information. The specification cautions against locally storing these values and says privacy-sensitive query data must not be cleartext.
- **Khả năng áp dụng vào Super App**: Implement lifecycle callbacks in the host container and use them for deterministic resource suspension/resumption, page-level analytics, crash/error reporting, cache cleanup, and sensitive-data redaction. Keep global and page state distinct, preserve state while hidden when policy allows, unload under resource pressure, and test that query/referrer data is not leaked into logs, analytics, or persistent storage.

### 3.5. [architecture] MiniApp White Paper positions a super app as a host platform using hybrid rendering, a JavaScript-worker logic layer, and controlled native bridges
- **Chuẩn tham chiếu**: W3C MiniApp Standardization White Paper version 2 — What is MiniApp; MiniApp/PWA comparison; separate view/logic layers; security and privacy considerations
- **Mức độ bằng chứng**: `industry_standard`
- **Nguồn kiểm chứng**: [https://w3c.github.io/miniapp-white-paper/](https://w3c.github.io/miniapp-white-paper/)
- **Nguồn bổ trợ**: [https://w3c.github.io/miniapp-manifest/](https://w3c.github.io/miniapp-manifest/), [https://w3c.github.io/miniapp-packaging/](https://w3c.github.io/miniapp-packaging/), [https://w3c.github.io/miniapp-addressing/](https://w3c.github.io/miniapp-addressing/), [https://w3c.github.io/miniapp-lifecycle/](https://w3c.github.io/miniapp-lifecycle/)
- **Chi tiết kỹ thuật**: The White Paper defines a super app as a software platform that hosts and supports other applications, and contrasts MiniApps with PWAs: MiniApps are bound to a specific platform/super app and are packed/self-contained, while PWA resources are distributed across the Web. Its architecture separates a View layer (Web and native components, hybrid rendering) from a Logic layer implemented with JavaScript Workers for events, API calls, and lifecycle; a JavaScript Bridge mediates access to host/OS capabilities such as payment, scanning, files, and calls. Rendering can be stateless while state lives in the worker, enabling parallel rendering and native page-stack management. The document describes widgets as URI-addressed host content with isolated data between host/widgets and between widgets, and notes that MiniApps in one host environment are independent. Its platform-security model includes capability authentication, user authorization, pre-publication audit, configured HTTPS/domain allowlists, and multiple permission levels. This is an architectural/industry reference rather than a standalone conformance specification; the normative package guidance is in MiniApp Packaging.
- **Khả năng áp dụng vào Super App**: Use the architecture as a store reference model: catalog/review services manage manifests, packages, permissions, domains, signatures, and versions; the host runtime owns isolated rendering/worker contexts and a narrowly allowlisted native bridge; lifecycle and addressing provide the control-plane events and entry points. Separate store trust/review from runtime enforcement, and require consent/audit evidence for high-risk capabilities instead of treating WebView isolation alone as a security boundary.

### 3.6. [TUF multi-role trust model for mini-app package metadata] Separate Root, Targets, Snapshot, and Timestamp trust with threshold signatures
- **Chuẩn tham chiếu**: TUF Specification 1.x, §§1.5, 2.1 (Root, Targets, Snapshot, Timestamp), and 5.4–5.7
- **Mức độ bằng chứng**: `normative_standard`
- **Nguồn kiểm chứng**: [https://theupdateframework.io/specification/latest/](https://theupdateframework.io/specification/latest/)
- **Nguồn bổ trợ**: [https://theupdateframework.io/overview/](https://theupdateframework.io/overview/)
- **Chi tiết kỹ thuật**: [NORMATIVE] TUF defines four fundamental top-level roles: Root, Targets, Snapshot, and Timestamp. Root delegates trust to keys for the other roles; Targets signs metadata describing trusted target files and may delegate full or partial trust; Snapshot records the latest versions of top-level and delegated targets metadata and prevents mix-and-match; Timestamp periodically signs a statement containing the Snapshot hash to prevent replay of out-of-date signed metadata. Every role may use multiple keys and a signature threshold, and clients ship trusted root keys for each configured repository. [SUPER-APP DESIGN] Treat each mini-app package and its release metadata as TUF targets, pin the catalog Root trust anchor in the host/store verifier, and use separate delegated Targets roles for publisher, tenant, or app namespaces with an explicit threshold (for example, a reviewed multi-party release policy). Verify the complete Timestamp→Snapshot→Targets chain before install or update and then verify the package digest and length. A compromised CDN edge can serve bytes but cannot authorize an arbitrary package unless the trusted signing threshold or client Root trust is also compromised; TLS/CDN provenance is transport evidence, not the package trust anchor.
- **Khả năng áp dụng vào Super App**: Use TUF at the client package-fetch boundary and at the catalog service. Keep Root keys offline and outside mini-app JavaScript; scope delegated roles so one publisher or tenant cannot sign another tenant’s namespace; make install, update, rollback, and quarantine decisions only after host-side threshold and digest verification.

### 3.7. [SLSA v1.0 mini-app developer submission provenance] Require digest-bound provenance for every submitted mini-app artifact
- **Chuẩn tham chiếu**: SLSA v1.0 Build track, Producing artifacts requirements and Provenance predicate
- **Mức độ bằng chứng**: `normative_standard`
- **Nguồn kiểm chứng**: [https://slsa.dev/spec/v1.0/requirements](https://slsa.dev/spec/v1.0/requirements)
- **Nguồn bổ trợ**: [https://slsa.dev/spec/v1.0/provenance](https://slsa.dev/spec/v1.0/provenance), [https://slsa.dev/spec/v1.0/levels](https://slsa.dev/spec/v1.0/levels), [https://slsa.dev/spec/v1.0/](https://slsa.dev/spec/v1.0/)
- **Chi tiết kỹ thuật**: [NORMATIVE] SLSA v1.0 requires a producer to choose a build platform capable of the desired level, follow a consistent build process, and distribute provenance to consumers. The build platform must generate provenance that unambiguously identifies the output package by cryptographic digest and describes how it was produced. The recommended predicate records the builder.id, buildType, externalParameters (untrusted inputs that must be included and verified downstream), resolvedDependencies when known, and subject artifacts. Build L1 provides provenance but may be incomplete or unsigned and is trivial to forge; L2 adds hosted-platform provenance with authenticity validation, while L3 adds strong anti-forgery controls. [SUPER-APP DESIGN] At submission, require an attestation for the exact mini-app archive/digest, source repository and commit, build template/version, manifest and lockfile inputs, builder identity, and relevant dependency resolutions. The store should compare those values with the registered publisher and release policy, reject a missing or digest-mismatched attestation, and retain provenance beside the package and TUF target metadata. Do not describe SLSA L1 as non-falsifiable; use L2 or L3 controls when the store needs provenance authenticity and resistance to tenant forgery.
- **Khả năng áp dụng vào Super App**: Creates an auditable link from a developer submission to source, builder, inputs, and package bytes. The store can require provenance before review/publication and can bind the provenance subject digest to the TUF Targets entry, preventing a valid attestation for one archive from being reused for another.

### 3.8. [SLSA v1.0 hosted and isolated store builds] Use hosted, isolated, control-plane-generated provenance for multi-tenant store builds
- **Chuẩn tham chiếu**: SLSA v1.0 Build L2 and Build L3; Producing artifacts requirements for authentic and unforgeable provenance
- **Mức độ bằng chứng**: `normative_standard`
- **Nguồn kiểm chứng**: [https://slsa.dev/spec/v1.0/levels](https://slsa.dev/spec/v1.0/levels)
- **Nguồn bổ trợ**: [https://slsa.dev/spec/v1.0/requirements](https://slsa.dev/spec/v1.0/requirements), [https://slsa.dev/spec/v1.0/provenance](https://slsa.dev/spec/v1.0/provenance), [https://slsa.dev/spec/v1.0/whats-new](https://slsa.dev/spec/v1.0/whats-new)
- **Chi tiết kỹ thuật**: [NORMATIVE] SLSA Build L2 means builds run on a hosted platform that generates and signs provenance, with downstream validation of provenance authenticity. Build L3 requires strong controls to prevent one run from influencing another, including runs within the same project, and to prevent provenance-signing secret material from being accessible to user-defined build steps. The v1.0 requirements further place provenance generation in the trusted control plane and require controls against tenant tampering; all required provenance fields must be generated or verified by that control plane. [SUPER-APP DESIGN] Build store releases in a dedicated hosted service with per-run isolation, immutable inputs, a control-plane signer, and no publisher-supplied signing key in the build container. Verify the provenance before publication, require builder/workflow identity and expected parameters, and bind the resulting subject digest to the TUF Targets record. Quarantine when a co-tenant, compromised upload credential, build cache, or user step could alter the attestation. SLSA describes strong resistance and verification guarantees, not an absolute claim that an artifact is safe or mathematically impossible to forge.
- **Khả năng áp dụng vào Super App**: Directly addresses malicious or compromised mini-app submissions in a shared store build farm. L2 is a practical minimum for signed hosted provenance; L3 is the target for sensitive capabilities or high-risk packages because it limits cross-tenant build influence and keeps attestation keys outside developer-controlled steps.

### 3.9. [Sigstore keyless signing Fulcio OIDC and Rekor transparency] Bind publisher identity and build attestations to package digests with Sigstore
- **Chuẩn tham chiếu**: Sigstore keyless signing architecture; Fulcio Certificate Authority; Rekor transparency log; Cosign verification
- **Mức độ bằng chứng**: `industry_standard`
- **Nguồn kiểm chứng**: [https://docs.sigstore.dev/cosign/signing/overview/](https://docs.sigstore.dev/cosign/signing/overview/)
- **Nguồn bổ trợ**: [https://docs.sigstore.dev/certificate_authority/overview/](https://docs.sigstore.dev/certificate_authority/overview/), [https://docs.sigstore.dev/logging/overview/](https://docs.sigstore.dev/logging/overview/), [https://docs.sigstore.dev/about/security/](https://docs.sigstore.dev/about/security/), [https://sigstore.dev/what-is-sigstore/](https://sigstore.dev/what-is-sigstore/)
- **Chi tiết kỹ thuật**: [INDUSTRY STANDARD] Sigstore documents keyless signing as associating an identity rather than a long-lived key with an artifact signature: Fulcio issues a short-lived certificate binding an ephemeral key to an OpenID Connect identity, and the signing event is recorded in Rekor. Fulcio’s official documentation describes short-lived X.509 certificates based on an OIDC identity (10-minute validity in the documented public service), while Rekor provides an immutable, tamper-resistant ledger with querying, inclusion-proof, and log-integrity verification capabilities. Sigstore’s security model uses OIDC authentication to prove account ownership and relies on transparency monitoring to make unauthorized certificates detectable. [SUPER-APP DESIGN] Have publisher CI sign both the mini-app artifact and its SLSA provenance, then require the store verifier to check the signature, Fulcio chain and issuer, registered publisher/repository/workflow identity claims, artifact digest, and Rekor inclusion before accepting the release. Monitor transparency entries for unexpected identities or duplicate/conflicting attestations. Keyless signing reduces long-lived developer-key distribution but does not establish build correctness, TUF freshness, or package safety; protect the OIDC account and CI workflow and combine Sigstore identity evidence with SLSA provenance and TUF metadata.
- **Khả năng áp dụng vào Super App**: Provides scalable publisher identity and public audit evidence for a multi-tenant store without distributing persistent private signing keys to every developer. Use it for package/provenance attestations, while TUF remains the client update/freshness layer and SLSA remains the build-integrity layer.

### 3.10. [permissions-policy/capability-delegation/permission-state] Use Permissions Policy as the host capability envelope before user consent
- **Chuẩn tham chiếu**: W3C Permissions Policy §§4.1, 4.3–4.5, 6.1–6.2, 9.4–9.10; W3C Permissions §5.1 and §6.3.4
- **Mức độ bằng chứng**: `normative_standard`
- **Nguồn kiểm chứng**: [https://w3c.github.io/webappsec-permissions-policy/](https://w3c.github.io/webappsec-permissions-policy/)
- **Nguồn bổ trợ**: [https://developer.mozilla.org/en-US/docs/Web/HTTP/Permissions_Policy](https://developer.mozilla.org/en-US/docs/Web/HTTP/Permissions_Policy), [https://w3c.github.io/permissions/](https://w3c.github.io/permissions/)
- **Chi tiết kỹ thuật**: [NORMATIVE FACT] Permissions Policy controls policy-controlled features independently of end-user permission: the HTTP Permissions-Policy header sets the document/descendant envelope, while an iframe allow attribute delegates only to a selected container. Allowlists support *, (), self, src, and explicit origins; parent policy and container policy are both evaluated, so an iframe cannot grant a feature that the parent header withheld. The current Permissions API specification describes this as permission delegation: most powerful features grant the top-level origin and delegate to the requesting document through Permissions Policy. When a policy-controlled feature is not allowed, the Permissions API permission state is denied and the user should not be prompted. PermissionStatus exposes granted/denied/prompt and asynchronously fires change/onchange when the state changes. [SUPER-APP CONTROL] Treat the header/iframe policy as a hard pre-consent gate: generate a per-mini-app allowlist from the registered capability manifest, default sensitive features to (), never use * for privileged device access, and query state before showing host UX. Bind the policy to the exact HTTPS origin/package release and tear down delegated frames on navigation or quarantine; browser permission consent must not substitute for host package identity or bridge authorization.
- **Khả năng áp dụng vào Super App**: For each mini-app, maintain separate declared, effective, and runtime capability sets. Emit a host-owned Permissions-Policy header and exact iframe allow directives from the effective set; require explicit review for camera, microphone, geolocation, bluetooth, sensors, and screen-wake-lock. Use navigator.permissions.query() plus PermissionStatus.onchange where supported to reconcile browser state with host state, and fail closed when policy, origin, or package identity does not match.

### 3.11. [geolocation/foreground-consent/high-accuracy/privacy] Make location access visible, foreground-bound, and precision-limited
- **Chuẩn tham chiếu**: W3C Geolocation §§2.7, 3.1–3.4, 6.5–6.7, 7.1, 9.1; Permissions Policy geolocation default allowlist
- **Mức độ bằng chứng**: `normative_standard`
- **Nguồn kiểm chứng**: [https://w3c.github.io/geolocation/](https://w3c.github.io/geolocation/)
- **Nguồn bổ trợ**: [https://developer.mozilla.org/en-US/docs/Web/API/Geolocation_API](https://developer.mozilla.org/en-US/docs/Web/API/Geolocation_API), [https://w3c.github.io/webappsec-permissions-policy/](https://w3c.github.io/webappsec-permissions-policy/)
- **Chi tiết kỹ thuật**: [NORMATIVE FACT] Geolocation is a secure-context powerful feature named geolocation. Its default allowlist is self, so cross-origin frames need explicit delegation; getCurrentPosition() and watchPosition() require express permission unless the existing state is already granted/denied. The request algorithm waits for a hidden document to become visible, and watch updates are delivered only to fully active, visible documents; user agents may rate-limit significant position changes. clearWatch() removes a watch. enableHighAccuracy is a request that the user agent may ignore, maximumAge permits a cached position, and the returned coordinates include an accuracy value; the API does not guarantee that the underlying source is the device's actual location. The specification recommends short permission lifetimes, commonly a session, and advises recipients to minimize use, retention, retransmission, and unauthorized access. [SUPER-APP CONTROL] Do not treat enableHighAccuracy as an entitlement or browser permission as background access. The host should show an app-specific consent sheet, allow location only while the mini-app is foreground/visible unless a separately reviewed native background capability exists, clear watches on pause/navigation/revocation, cap update frequency and retention, and return coarse or fuzzed coordinates through the host adapter when exact coordinates are unnecessary. Precision reduction/fuzzing is an additional host policy, not a promise made by the Geolocation API.
- **Khả năng áp dụng vào Super App**: Expose location as separate coarse-location, precise-location, and background-location capabilities with distinct review and consent. Record purpose, precision, update cadence, retention, and recipient scope per grant; deny undeclared precision escalation and invalidate cached location handles when the mini-app loses foreground status or the host revokes access.

### 3.12. [media-capture/camera/microphone/indicators/revocation] Gate camera and microphone per mini-app and make capture revocable
- **Chuẩn tham chiếu**: Media Capture and Streams: ConstrainablePattern/MediaStreamTrack lifecycle; Permissions Integration; Permissions Policy Integration; Privacy Indicator Requirements
- **Mức độ bằng chứng**: `normative_standard`
- **Nguồn kiểm chứng**: [https://w3c.github.io/mediacapture-main/](https://w3c.github.io/mediacapture-main/)
- **Nguồn bổ trợ**: [https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia), [https://w3c.github.io/webappsec-permissions-policy/](https://w3c.github.io/webappsec-permissions-policy/)
- **Chi tiết kỹ thuật**: [NORMATIVE FACT] Media Capture defines camera and microphone as powerful features and policy-controlled features with default allowlist self. If either policy feature is disabled in a document, content in that document cannot use getUserMedia() for the device, and enumerateDevices() exposes only devices the document is allowed to use. getUserMedia() requires a secure context and user permission; constraints select a source and operating range, can be changed later, and may fail with an overconstrained or not-allowed error. When a source is stopped, the user agent updates its live/access state; camera/microphone tracks can be muted by privacy controls or ended when the user rescinds permission. The specification requires user-visible indication when aggregate accessible/live capture state changes and encourages ongoing and hardware-light indicators. [SUPER-APP CONTROL] Keep camera and microphone grants separate, per app and per session/use case. Show a host-owned recording indicator that cannot be hidden by mini-app UI, stop tracks and invalidate capture handles on host revoke, navigation, background/quarantine, or renderer failure, and require the mini-app to reacquire permission. Treat constraints as resource limits rather than authorization: cap resolution/frame rate/channel count in the host policy, avoid exposing raw frames beyond the approved consumer, and log only capability events rather than media contents.
- **Khả năng áp dụng vào Super App**: A capability manifest should declare camera versus microphone, front/rear or device class, maximum resolution/frame rate, expected duration, and whether simultaneous capture is allowed. The host must require an exact origin/package match before iframe delegation, maintain an always-visible active-capture indicator, and propagate native permission revocation as track end/mute plus a typed bridge error.

### 3.13. [web-bluetooth/ble/gatt/service-filtering/permission] Constrain Web Bluetooth to user-selected devices and declared GATT services
- **Chuẩn tham chiếu**: MDN Web Bluetooth API security considerations; Bluetooth.requestDevice() filters, optionalServices, and Permissions Policy integration
- **Mức độ bằng chứng**: `industry_standard`
- **Nguồn kiểm chứng**: [https://developer.mozilla.org/en-US/docs/Web/API/Web_Bluetooth_API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Bluetooth_API)
- **Nguồn bổ trợ**: [https://developer.mozilla.org/en-US/docs/Web/API/Bluetooth/requestDevice](https://developer.mozilla.org/en-US/docs/Web/API/Bluetooth/requestDevice), [https://w3c.github.io/webappsec-permissions-policy/](https://w3c.github.io/webappsec-permissions-policy/)
- **Chi tiết kỹ thuật**: [PLATFORM/WEB API FACT] Web Bluetooth is limited to secure contexts and is controlled by the bluetooth Permissions Policy directive, whose default allowlist is self; cross-origin use requires both an allowed origin in the Permissions-Policy header and a matching iframe allow directive. A new device request requires explicit user permission and transient activation; navigator.permissions.query({name: "bluetooth"}) can report the permission state. requestDevice() supports filters over GATT services, names/prefixes, manufacturer data, service data, and exclusion filters. After pairing, a page may access only GATT service UUIDs listed in filters.services or optionalServices; acceptAllDevices requires optionalServices to make later service access possible. [SUPER-APP CONTROL] Treat Bluetooth as a high-risk, per-device capability rather than a generic radio switch: require a host confirmation naming the device and services, reject acceptAllDevices by default, intersect requested services with an app manifest allowlist, require foreground/transient activation, and avoid sharing prior device handles across package identities. On host revoke, disconnect/close the GATT session, clear the bridge capability, and force a fresh user gesture and grant; user permission is not proof that the peripheral or its data is trustworthy.
- **Khả năng áp dụng vào Super App**: Register each allowed BLE service UUID, characteristic operation (read/write/notify), device-selection rule, and session lifetime per mini-app release. The host should expose only the approved service facade, deny undeclared optionalServices, partition grants by exact origin and package identity, and treat all characteristic values and advertisement data as untrusted input.

### 3.14. [web-nfc/ndef/read-write/visibility/host-boundary] Keep Web NFC visible, NDEF-only, and read-before-write
- **Chuẩn tham chiếu**: Web NFC Community Group draft: Scope; NDEFReader; Obtaining permission; Handling visibility change; Releasing NFC; Writing content; NDEFWriteOptions
- **Mức độ bằng chứng**: `industry_standard`
- **Nguồn kiểm chứng**: [https://w3c-cg.github.io/web-nfc/](https://w3c-cg.github.io/web-nfc/)
- **Nguồn bổ trợ**: [https://developer.mozilla.org/en-US/docs/Web/API/Web_NFC_API](https://developer.mozilla.org/en-US/docs/Web/API/Web_NFC_API), [https://developer.mozilla.org/en-US/docs/Web/API/NDEFReader](https://developer.mozilla.org/en-US/docs/Web/API/NDEFReader), [https://developer.mozilla.org/en-US/docs/Web/API/NDEFReader/write](https://developer.mozilla.org/en-US/docs/Web/API/NDEFReader/write)
- **Chi tiết kỹ thuật**: [SPEC/DRAFT FACT] The Web NFC draft limits the API to NDEF use cases; low-level I/O such as ISO-DEP/NFC-A/B/NFC-F and host-based card emulation are outside its scope. NDEFReader is secure-context-only. The nfc powerful feature is permission-gated, and scan()/write() can trigger permission handling; the draft's visibility algorithm suspends NFC when the document is hidden, presents no received content while suspended, and attempts to abort pending writes. Unloading releases NFC resources. A write supports overwrite and AbortSignal controls, and the draft recommends the read-then-write flow so the app can inspect the tag before changing it. NDEF readings can include a tag serial number, which may be stable or randomized by the tag. [SUPER-APP CONTROL] Do not assume that an iframe allow="nfc" is a portable standard boundary: the current draft defines the nfc powerful feature and visibility/resource lifecycle but does not define a Permissions Policy integration section. The super-app must therefore enforce its own exact-origin/package embedder allowlist and native bridge gate. Require an explicit host confirmation immediately before write or makeReadOnly, read and validate the existing NDEF message first, cap record count/size/types, treat URLs/MIME/text/payloads as untrusted, avoid retaining serial numbers without purpose, abort pending operations on background/navigation/revoke, and never offer background NFC to an embedded mini-app.
- **Khả năng áp dụng vào Super App**: Model NFC read, write, and make-read-only as separate capabilities. Bind each to a visible user action and short-lived session, require schema validation and an app-specific tag namespace, keep the raw NDEF payload out of general telemetry, and invalidate the reader plus all pending promises when the mini-app leaves the foreground or the host closes the capability.

### 3.15. [generic-sensor/accelerometer/gyroscope/magnetometer/frequency/privacy] Throttle and foreground-bind motion sensors; do not promise a universal sensor rate
- **Chuẩn tham chiếu**: Generic Sensor §4.2.1–§4.2.5, §4.3.1–§4.3.4, §5.4–§5.5, §6.1, §8.6, §8.14
- **Mức độ bằng chứng**: `normative_standard`
- **Nguồn kiểm chứng**: [https://w3c.github.io/sensors/](https://w3c.github.io/sensors/)
- **Nguồn bổ trợ**: [https://w3c.github.io/permissions/](https://w3c.github.io/permissions/), [https://w3c.github.io/webappsec-permissions-policy/](https://w3c.github.io/webappsec-permissions-policy/), [https://developer.mozilla.org/en-US/docs/Web/API/Permissions/query](https://developer.mozilla.org/en-US/docs/Web/API/Permissions/query)
- **Chi tiết kỹ thuật**: [NORMATIVE FACT] Generic Sensor requires secure context, Permissions Policy permission for the sensor type, the Permissions API, a visible document, and a successful focus-and-origin check before readings are exposed. The requested SensorOptions.frequency is bounded by implementation- and device-defined minimum/maximum sampling frequencies; reporting frequency cannot exceed platform acquisition frequency or the device maximum, and the actual calculation is implementation-defined. Sensor types can define permission names, policy feature names, bounds, threshold checks, and reading quantization. The privacy section identifies location inference, eavesdropping, keystroke monitoring, fingerprinting, and cross-sensor correlation as threats, and lists maximum-frequency limits, stopping the sensor, limiting delivered readings, and reducing/quantizing accuracy as mitigations. Permission revocation deactivates live sensors and queues a NotAllowedError. [SUPER-APP CONTROL] Treat accelerometer, gyroscope, and magnetometer as separate high-risk capabilities; do not promise a fixed Hz value across devices. Set host-side ceilings for frequency, readings per session, timestamp precision, and retention; quantize or aggregate data where possible; stop or suspend sensors on background/hidden/inactive state; and deny combinations that create a tracking or keystroke-inference channel. The host should expose only the minimum sensor axes and derived events required by the mini-app.
- **Khả năng áp dụng vào Super App**: Require a declared purpose and sensor set in the mini-app manifest, with a foreground-only default. Enforce the effective cap in the native/host adapter rather than trusting the requested frequency, propagate revocation as a typed error, and keep raw motion streams out of persistent logs unless a reviewed diagnostic purpose exists.

### 3.16. [screen-wake-lock/visibility/release/battery] Treat screen wake lock as a visible, revocable, budgeted capability
- **Chuẩn tham chiếu**: Screen Wake Lock API: Policy control; Permissions and user prompts; WakeLock.request(); WakeLockSentinel.release()/onrelease; automatic wake-lock management
- **Mức độ bằng chứng**: `normative_standard`
- **Nguồn kiểm chứng**: [https://w3c.github.io/screen-wake-lock/](https://w3c.github.io/screen-wake-lock/)
- **Nguồn bổ trợ**: [https://w3c.github.io/webappsec-permissions-policy/](https://w3c.github.io/webappsec-permissions-policy/), [https://w3c.github.io/permissions/](https://w3c.github.io/permissions/)
- **Chi tiết kỹ thuật**: [NORMATIVE FACT] Screen Wake Lock is secure-context-only and a policy-controlled feature named screen-wake-lock with default allowlist self; third-party frames need explicit allow delegation, and a header can disable it with screen-wake-lock=(). request() rejects when the document is not fully active, not policy-allowed, denied by the user agent, or hidden. Acquisition is advisory: low battery, power-saving mode, OS policy, or other implementation conditions may prevent or later release the underlying lock. A sentinel represents the active handle, release() is idempotent, onrelease reports user-agent release, and wake locks are released when the document loses full activity or visibility. [SUPER-APP CONTROL] Keep wake lock foreground-only by default, enforce a maximum duration and battery/power budget in the host, release it on mini-app pause/background/navigation/revoke, and show host-owned UI identifying the app that is keeping the screen awake. Never treat a resolved request() promise as proof that the OS will keep the screen on; the mini-app must handle onrelease and be prepared to fall back.
- **Khả năng áp dụng vào Super App**: Declare wake-lock purpose (navigation, scan, presentation, or accessibility), expected duration, and whether the app may reacquire after release. Require an exact origin/package match before iframe delegation, rate-limit reacquisition, deny hidden/background requests, and record only grant/release/reason events rather than continuous device state.

## 4. Khuyến nghị Kiến trúc & Triển khai cho Super App Store

1. **Mô hình Khởi chạy & Bao đóng chuẩn W3C MiniApp**:
   - Super App Container triển khai mô hình đa luồng: Luồng View chạy Webview/Render độc lập, Luồng Logic chạy trong JavaScript Web Worker hoặc V8 Isolate cô lập, giao tiếp với Native Bridge thông qua cơ chế Messaging có kiểm soát.
   - Chuẩn hóa định dạng gói `.zip` theo W3C MiniApp Packaging với `manifest.json` tại thư mục gốc, hỗ trợ phân chia subpackages cho các mini app lớn.

2. **Bảo mật Cập nhật và Toàn vẹn Chuỗi cung ứng (TUF + SLSA + Sigstore)**:
   - Áp dụng mô hình 4 vai trò của TUF (Root, Targets, Snapshot, Timestamp) tại Catalog Service của Store để đảm bảo client Super App không bao giờ tải phải bản build cũ bị lỗ hổng (anti-rollback) hoặc snapshot giả mạo từ CDN cache.
   - Bắt buộc Developer CLI ký gói bằng Sigstore/Cosign với danh tính OIDC được cấp phép bởi Super App Developer Portal; Store Build Engine xuất SLSA Provenance v1.0 Level 2/3 cho mọi bản phát hành chính thức.

3. **Quản trị Thiết bị Ngoại vi & Cảm biến (Permissions Policy Sandbox)**:
   - Thiết lập header/chính sách `Permissions-Policy` làm rào chắn cấp 1 tại cấp độ Container. Mọi quyền truy cập phần cứng nhạy cảm (Camera, Mic, GPS chính xác, Bluetooth, NFC, Wake Lock) phải được khai báo trước trong `manifest.json`.
   - Triển khai Foreground Liveness Gate: tự động hủy hoặc tạm ngưng các stream cảm biến/phần cứng khi Mini App bị ẩn (`onHide`) hoặc chuyển sang background; hiển thị trực quan chỉ báo phần cứng đang hoạt động (privacy indicators) trên thanh tiêu đề của Super App.
