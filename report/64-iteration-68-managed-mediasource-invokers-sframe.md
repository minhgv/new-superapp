# Chuyên đề 64: W3C ManagedMediaSource API, WHATWG Invoker Commands & IETF RFC 9605 Secure Frame (SFrame)

## 1. Tổng quan Nghiên cứu & Định vị Chuẩn (Milestone 68)

Trong khuôn khổ Milestone 68, nghiên cứu tập trung vào 3 trụ cột kỹ thuật nền tảng của web platform hiện đại, tối ưu hóa phần cứng di động và kiến trúc mật mã zero-trust:
1. **W3C ManagedMediaSource API (MSE v2)**: Giải quyết sự đánh đổi lịch sử giữa tính linh hoạt của JavaScript MSE và hiệu suất năng lượng của native HLS. Cho phép trình duyệt điều tiết lưu lượng nạp đoạn video (burst downloading), tự động dọn dẹp frame đệm khi thiết bị chịu áp lực bộ nhớ (Coded Frame Eviction) và đưa modem 5G NR vào chế độ RRC sleep để tiết kiệm pin tối đa.
2. **WHATWG Invoker Commands API (`commandfor` & `command`)**: Chuẩn hóa cơ chế kích hoạt hành vi giao diện người dùng theo mô hình khai báo trực tiếp trong HTML. Loại bỏ hoàn toàn mã JavaScript gắn sự kiện `addEventListener('click')` thủ công, cung cấp các hành vi tích hợp sẵn (`show-modal`, `close`, `request-close`, `toggle-popover`), khả năng mở rộng với cú pháp `--custom-action`, và sự kiện non-bubbling, composed `CommandEvent` bảo toàn khả năng chặn duyệt (`preventDefault`).
3. **IETF RFC 9605 Secure Frame (SFrame)**: Chuẩn hóa mật mã hóa đầu-cuối (E2EE) cho hội nghị âm thanh/video đa điểm, cho phép các máy chủ chuyển tiếp chọn lọc (Selective Forwarding Units - SFU) định tuyến luồng media dựa trên header mà không thể giải mã nội dung âm thanh/hình ảnh. Đóng gói header siêu gọn nhẹ (1-8 octets KID + CTR) kết hợp thuật toán AEAD (AES-GCM, ChaCha20-Poly1305) và cửa sổ trượt chống phát lại (anti-replay window) tích hợp mượt mà trong Web Workers qua WebRTC Encoded Transform.

## 3. Phân tích Kỹ thuật Chi tiết Từng Phát hiện

### managed_media_source_068_01: W3C ManagedMediaSource API & Power-Efficient Adaptive Video Streaming
- **Chủ đề**: `managed_media_source_api_architecture` | **Nhóm chuyên mục**: `Operational Reliability, SRE, Recovery & Observability`
- **Mức bằng chứng**: `specification` | **Chuẩn tham chiếu**: W3C Media Source Extensions v2 §4 ManagedMediaSource Interface
- **URL Chuẩn**: [https://www.w3.org/TR/media-source-2/](https://www.w3.org/TR/media-source-2/)
- **Nguồn hỗ trợ / Triển khai**: [https://developer.mozilla.org/en-US/docs/Web/API/ManagedMediaSource](https://developer.mozilla.org/en-US/docs/Web/API/ManagedMediaSource), [https://developer.apple.com/videos/play/wwdc2023/10122/](https://developer.apple.com/videos/play/wwdc2023/10122/)
- **Tóm tắt cốt lõi**: ManagedMediaSource transfers buffer lifecycle and network pacing control back to the user agent, optimizing streaming efficiency, battery life, and high-speed radio usage.
- **Phân tích kỹ thuật chuyên sâu & Kiến trúc Super-App**:
  [SPEC FACT] The W3C Media Source Extensions v2 specification introduces the 'ManagedMediaSource' interface (inheriting from MediaSource) to address critical performance and battery drain inefficiencies in client-driven adaptive streaming. While traditional MSE granted JavaScript applications complete, unconstrained control over segment appending, it lacked visibility into system memory pressure, modem power states, and hardware decoders. ManagedMediaSource empowers the user agent to actively signal optimal fetching windows and autonomously evict inactive buffer ranges when physical memory is constrained. [SUPERAPP ARCHITECTURE] Super-app mini-apps frequently embed rich video experiences (e.g., short-video feeds, live shopping streams, educational webinars). On resource-constrained mobile devices running multiple backgrounded mini-apps, legacy MSE video players cause aggressive battery depletion and Out-Of-Memory (OOM) OS process termination by over-buffering ahead of the playhead. By enforcing ManagedMediaSource in the super-app media player component, the container coordinates with underlying mobile power governors to conserve CPU cycles and battery without degrading playback continuity.

### managed_media_source_068_02: ManagedMediaSource 'streaming' Property and startstreaming/endstreaming Events
- **Chủ đề**: `managed_media_source_streaming_lifecycle_events` | **Nhóm chuyên mục**: `Operational Reliability, SRE, Recovery & Observability`
- **Mức bằng chứng**: `specification` | **Chuẩn tham chiếu**: W3C Media Source Extensions v2 §4.1 streaming attribute & streaming events
- **URL Chuẩn**: [https://developer.mozilla.org/en-US/docs/Web/API/ManagedMediaSource](https://developer.mozilla.org/en-US/docs/Web/API/ManagedMediaSource)
- **Nguồn hỗ trợ / Triển khai**: [https://www.w3.org/TR/media-source-2/](https://www.w3.org/TR/media-source-2/), [https://developer.apple.com/videos/play/wwdc2023/10122/](https://developer.apple.com/videos/play/wwdc2023/10122/)
- **Tóm tắt cốt lõi**: The 'streaming' boolean property and paired 'startstreaming' and 'endstreaming' events signal to web applications exactly when to fetch segments or allow modems to enter low-power sleep states.
- **Phân tích kỹ thuật chuyên sâu & Kiến trúc Super-App**:
  [SPEC FACT] ManagedMediaSource exposes a read-only boolean attribute 'streaming' and dispatches two core lifecycle events: 'startstreaming' and 'endstreaming'. When 'streaming' is true, the user agent indicates that buffer levels are low, a user-initiated seek has occurred into an unbuffered region, or network conditions are optimal for burst downloading, prompting the application to fetch segments via fetch(). When 'streaming' transitions to false, the user agent indicates that sufficient forward buffer has been accumulated. The application must suspend outbound segment requests, allowing cellular and Wi-Fi modems to power down into low-power sleep states. [SUPERAPP ARCHITECTURE] Continuous background segment polling by mini-app media players is a leading contributor to device thermal throttling and cellular radio battery drain. The super-app SDK abstracts player engines (e.g., HLS.js or Shaka Player) to subscribe to 'startstreaming' and 'endstreaming'. The engine suspends chunk fetching immediately upon 'endstreaming' and resumes upon 'startstreaming'. Automated store performance testing verifies that mini-app video players do not emit network requests while streaming is false, preventing store rejection for battery inefficiency.

### managed_media_source_068_03: ManagedSourceBuffer & Autonomous 'bufferedchange' Coded Frame Eviction
- **Chủ đề**: `managed_source_buffer_bufferedchange_eviction` | **Nhóm chuyên mục**: `Operational Reliability, SRE, Recovery & Observability`
- **Mức bằng chứng**: `specification` | **Chuẩn tham chiếu**: W3C Media Source Extensions v2 §5 ManagedSourceBuffer & BufferedChangeEvent
- **URL Chuẩn**: [https://developer.mozilla.org/en-US/docs/Web/API/ManagedSourceBuffer](https://developer.mozilla.org/en-US/docs/Web/API/ManagedSourceBuffer)
- **Nguồn hỗ trợ / Triển khai**: [https://developer.mozilla.org/en-US/docs/Web/API/ManagedMediaSource](https://developer.mozilla.org/en-US/docs/Web/API/ManagedMediaSource), [https://www.w3.org/TR/media-source-2/](https://www.w3.org/TR/media-source-2/)
- **Tóm tắt cốt lõi**: ManagedSourceBuffer allows the user agent to run coded frame eviction algorithms at any time under memory pressure, dispatching 'bufferedchange' events to notify the application.
- **Phân tích kỹ thuật chuyên sâu & Kiến trúc Super-App**:
  [SPEC FACT] When 'addSourceBuffer(type)' is invoked on a ManagedMediaSource instance, it creates a 'ManagedSourceBuffer' rather than a standard SourceBuffer. Unlike standard SourceBuffers, which only evict frames during an active appendBuffer() call, a ManagedSourceBuffer permits the user agent's media engine to execute the 'Coded Frame Eviction' algorithm asynchronously at any time in response to system memory pressure. Upon purging unplayed or distant past buffer ranges, the user agent fires a 'bufferedchange' event containing 'addedRanges' and 'removedRanges' TimeRanges, notifying JavaScript that previously loaded ranges must be re-requested if the playhead seeks back. [SUPERAPP ARCHITECTURE] When a user switches between mini-apps in a super-app (e.g., pausing an e-learning video to approve a payment in a banking mini-app), the host container faces aggressive RAM pressure from the newly active webview. ManagedSourceBuffer allows the browser engine to silently purge cached 4K/1080p video frames from the paused mini-app without crashing the process. The mini-app's bufferedchange listener updates its internal index, seamlessly fetching evicted segments only if the user resumes playback.

- **Tóm tắt cốt lõi**: ManagedMediaSource enables mobile operating systems to burst video data over high-power 5G modems and return radios to low-power RRC idle states, reducing cellular power drain.
- **Phân tích kỹ thuật chuyên sâu & Kiến trúc Super-App**:
  [SPEC FACT] Cellular radios operating on 5G New Radio (NR) networks consume substantially higher instantaneous power when the radio frequency (RF) transceiver is active in Radio Resource Control (RRC) Connected mode compared to RRC Idle/Inactive mode. Traditional MSE fetches small 2-to-4-second video chunks at frequent intervals, keeping the cellular modem continuously active and generating severe battery drain. ManagedMediaSource allows the browser to calculate optimal burst transfer windows, downloading larger segment batches at gigabit 5G speeds during 'startstreaming' and quickly allowing the modem to power down into sleep states. [SUPERAPP ARCHITECTURE] Super-app mobile frameworks implement network intelligence telemetry that monitors active connection types (via Network Information API) and aligns mini-app streaming policies. In 5G cellular environments, the container configures ManagedMediaSource buffering thresholds to maximize burst efficiency, preventing micro-buffering requests from sustaining high-power modem states. Store certification audits verify that streaming video mini-apps comply with burst-and-sleep radio profiles.

### managed_media_source_068_05: Off-Thread ManagedMediaSource Construction in Dedicated Web Workers
- **Chủ đề**: `managed_media_source_dedicated_worker_offloading` | **Nhóm chuyên mục**: `Operational Reliability, SRE, Recovery & Observability`
- **Mức bằng chứng**: `specification` | **Chuẩn tham chiếu**: W3C Media Source Extensions v2 §4.2 DedicatedWorkerGlobalScope Integration
- **URL Chuẩn**: [https://www.w3.org/TR/media-source-2/](https://www.w3.org/TR/media-source-2/)
- **Nguồn hỗ trợ / Triển khai**: [https://developer.mozilla.org/en-US/docs/Web/API/ManagedMediaSource](https://developer.mozilla.org/en-US/docs/Web/API/ManagedMediaSource), [https://developer.mozilla.org/en-US/docs/Web/API/ManagedSourceBuffer](https://developer.mozilla.org/en-US/docs/Web/API/ManagedSourceBuffer)
- **Tóm tắt cốt lõi**: Constructing ManagedMediaSource inside Dedicated Web Workers offloads segment fetching, demuxing, and buffer appending from the main UI thread, preserving Core Web Vitals INP.
- **Phân tích kỹ thuật chuyên sâu & Kiến trúc Super-App**:
  [SPEC FACT] W3C MSE v2 formalizes the construction of ManagedMediaSource instances inside 'DedicatedWorkerGlobalScope'. By checking 'ManagedMediaSource.canConstructInDedicatedWorker' or passing the MediaSource handle via 'MediaProvider' / 'createObjectURL' back to the main thread HTMLMediaElement, web applications can execute data fetching (fetch/ReadableStream), cryptographic decryption, and SourceBuffer appending entirely off the main thread. This completely decouples heavy ArrayBuffer manipulation and WebM/ISOBMFF demuxing from the UI rendering thread. [SUPERAPP ARCHITECTURE] In interactive mini-apps (such as live commerce where video plays alongside real-time chat, product carousels, and checkout sheets), executing appendBuffer() on the main thread causes significant jank and degrades Interaction to Next Paint (INP > 200ms). The super-app standard mandates that third-party streaming mini-apps execute media buffering inside a Dedicated Web Worker when ManagedMediaSource worker support is available. This guarantees 60fps UI responsiveness during intense video segment processing.

- **Tóm tắt cốt lõi**: Invoker Commands allow <button> elements to declaratively control popovers, dialogs, and custom targets via 'commandfor' and 'command' attributes without JavaScript event boilerplate.
- **Phân tích kỹ thuật chuyên sâu & Kiến trúc Super-App**:
  [SPEC FACT] The Invoker Commands API adds 'commandfor' (an IDREF pointing to a target element in the document) and 'command' (a built-in or custom action identifier) attributes to HTMLButtonElement. When the button is activated via any Human Input Device (click, touch, Space, or Enter key), the browser natively dispatches a 'CommandEvent' on the target element and executes default platform behaviors without requiring userland 'addEventListener('click')' scripting. If 'command' is missing or unrecognized without custom prefixing, it defaults to an invalid state where no action occurs, preventing accidental triggers. [SUPERAPP ARCHITECTURE] Lightweight mini-app architectures require high performance and minimal initial JavaScript bundle sizes. By leveraging declarative 'commandfor' and 'command', mini-app UI templates can wire up interactive dialogs, menus, and bottom sheets directly in parsed HTML markup before client-side hydration or framework bundles finish executing. This delivers immediate interactive responsiveness on low-end devices and cuts hundreds of lines of fragile event-binding boilerplate across mini-app components.

- **Tóm tắt cốt lõi**: Custom invoker commands must use the '--' dashed-ident namespace, guaranteeing that custom application actions will never conflict with future standardized platform commands.
- **Phân tích kỹ thuật chuyên sâu & Kiến trúc Super-App**:
  [SPEC FACT] Web authors can define custom actions on any DOM element by assigning a command value starting with a double dash ('--'), adopting the CSS dashed-ident convention (e.g., command="--add-to-cart" or command="--rotate-card"). Browsers normatively guarantee that native built-in commands will never begin with '--'. When a button with a custom command is invoked, the user agent dispatches a CommandEvent on the target element with 'event.command' reflecting the dashed string and 'event.source' referencing the invoking button element, allowing component logic to handle the interaction cleanly. [SUPERAPP ARCHITECTURE] Mini-app design systems and Web Components (e.g., custom tabs, carousels, or audio players) use custom invoker commands to decouple triggers from target components. An add-to-cart button can declare 'commandfor="cart-drawer" command="--add-item" value="item-12345"', firing a typed CommandEvent directly on the cart component. This eliminates spaghetti querySelector code and event bus subscriptions, creating clean, testable component boundaries within mini-app runtimes.

### invoker_commands_068_04: CommandEvent Interface, Event Lifecycle, and Cancelable Side-Effect Control
- **Chủ đề**: `invoker_commands_command_event_lifecycle` | **Nhóm chuyên mục**: `Security Architecture, Sandboxing & Vulnerability Management`
- **Mức bằng chứng**: `specification` | **Chuẩn tham chiếu**: WHATWG HTML / Open UI Invoker Commands §5 CommandEvent Interface & Dispatch
- **URL Chuẩn**: [https://developer.mozilla.org/en-US/docs/Web/API/CommandEvent](https://developer.mozilla.org/en-US/docs/Web/API/CommandEvent)
- **Nguồn hỗ trợ / Triển khai**: [https://open-ui.org/components/invokers.explainer/](https://open-ui.org/components/invokers.explainer/), [https://developer.mozilla.org/en-US/docs/Web/API/Invoker_Commands_API](https://developer.mozilla.org/en-US/docs/Web/API/Invoker_Commands_API)
- **Tóm tắt cốt lõi**: CommandEvent is a non-bubbling, composed, trusted, and cancelable event fired on the target element, allowing script handlers to intercept or prevent default browser actions.
- **Phân tích kỹ thuật chuyên sâu & Kiến trúc Super-App**:
  [SPEC FACT] The 'CommandEvent' interface extends the base DOM Event. Crucially, CommandEvents are non-bubbling (bubbles: false), composed (composed: true, crossing Shadow DOM boundaries), trusted (isTrusted: true when initiated by real user input), and cancelable (cancelable: true). If a web author attaches an 'addEventListener("command", (e) => ...)' listener to the target element and calls 'event.preventDefault()', the browser skips the default built-in action (such as opening the dialog or hiding the popover). Event handlers can read 'event.source' to inspect the button that initiated the command and 'event.command' to identify the requested action. [SUPERAPP ARCHITECTURE] Super-app security frameworks leverage CommandEvent's cancelable lifecycle to enforce security and business integrity checks before modals open. For example, before a sensitive financial transfer confirmation dialog is displayed, the mini-app's command listener verifies transaction preconditions or rate limits; if validation fails, 'event.preventDefault()' cancels dialog rendering. Furthermore, because CommandEvent has 'isTrusted: true', host security bridges can verify that actions originated from physical user clicks rather than synthetic click() injection.

### sframe_e2ee_068_01: IETF RFC 9605 Secure Frame (SFrame) & Zero-Trust Media Conferencing Architecture
- **Chủ đề**: `sframe_architecture_sfu_zero_trust` | **Nhóm chuyên mục**: `Security Architecture, Sandboxing & Vulnerability Management`
- **Mức bằng chứng**: `specification` | **Chuẩn tham chiếu**: IETF RFC 9605 Secure Frame (SFrame) §1 Introduction & §3 Architecture
- **URL Chuẩn**: [https://datatracker.ietf.org/doc/html/rfc9605](https://datatracker.ietf.org/doc/html/rfc9605)
- **Nguồn hỗ trợ / Triển khai**: [https://datatracker.ietf.org/wg/sframe/about/](https://datatracker.ietf.org/wg/sframe/about/), [https://www.rfc-editor.org/subjects/sframe/](https://www.rfc-editor.org/subjects/sframe/)
- **Tóm tắt cốt lõi**: RFC 9605 standardizes SFrame, providing lightweight authenticated end-to-end encryption for media frames so central media servers (SFUs) route streams without access to plaintext audio/video.
- **Phân tích kỹ thuật chuyên sâu & Kiến trúc Super-App**:
  [SPEC FACT] IETF RFC 9605 defines Secure Frame (SFrame), an end-to-end encryption (E2EE) and authentication format for multi-party audio and video media. Unlike traditional WebRTC hop-by-hop SRTP encryption—where the central Selective Forwarding Unit (SFU) decrypts all media to inspect RTP headers and re-encrypts toward recipients—SFrame encrypts media at the frame level before packetization. The central media routing server (SFU) can inspect unencrypted RTP transport metadata and SFrame headers to make dynamic switching, bitrate adaptation, and forwarding decisions, but remains mathematically barred from accessing plaintext audio or video data. [SUPERAPP ARCHITECTURE] Super-app mini-apps increasingly embed real-time collaboration, telemedicine consultations, enterprise board meetings, and private social video calling. Entrusting cloud SFU media servers with unencrypted corporate or health conversations exposes the super-app ecosystem to massive data breach and wiretapping liabilities. By standardizing on RFC 9605 SFrame, mini-apps achieve zero-trust real-time communications: media payloads are encrypted with client keys inside the mini-app sandbox, ensuring that intermediate super-app routing servers and cloud SFUs never possess plaintext audio or video data.

### sframe_e2ee_068_02: SFrame Frame Format: Key ID, Counter (CTR), and AEAD Encapsulation
- **Chủ đề**: `sframe_frame_header_encapsulation_format` | **Nhóm chuyên mục**: `Security Architecture, Sandboxing & Vulnerability Management`
- **Mức bằng chứng**: `specification` | **Chuẩn tham chiếu**: IETF RFC 9605 §4 SFrame Frame Format & §4.1 Header
- **URL Chuẩn**: [https://datatracker.ietf.org/doc/html/rfc9605](https://datatracker.ietf.org/doc/html/rfc9605)
- **Nguồn hỗ trợ / Triển khai**: [https://datatracker.ietf.org/wg/sframe/about/](https://datatracker.ietf.org/wg/sframe/about/), [https://www.rfc-editor.org/subjects/sframe/](https://www.rfc-editor.org/subjects/sframe/)
- **Tóm tắt cốt lõi**: SFrame header specifies a compact 1-to-8 byte Key ID (KID), a monotonically increasing Counter (CTR) for nonce generation, and an AEAD authentication tag, minimizing packet overhead.
- **Phân tích kỹ thuật chuyên sâu & Kiến trúc Super-App**:
  [SPEC FACT] Under RFC 9605 §4, an SFrame-protected payload consists of an SFrame Header followed by the AEAD ciphertext and authentication tag. The header contains a flexible Key ID (KID) identifying the sender's active cryptographic key, encoded as a compact variable-length integer (1 to 8 octets), and a Counter (CTR) field representing a monotonically increasing frame counter. SFrame derives a unique initialization vector (IV/nonce) for each frame by XORing the frame counter with a salt derived from the sender key, completely eliminating nonce-reuse vulnerabilities across high-framerate video streams while maintaining minimal byte overhead. [SUPERAPP ARCHITECTURE] Mobile bandwidth in emerging markets is constrained and sensitive to protocol bloat. Legacy application-layer wrapper protocols introduced 40-80 bytes of overhead per packet, degrading mobile radio performance and causing fragmentation. SFrame's compact header structure introduces as little as 4-6 bytes of overhead per media frame, enabling multi-party 60fps video calling and spatial audio in mini-apps without incurring packet MTU fragmentation or radio bandwidth penalties.

- **URL Chuẩn**: [https://datatracker.ietf.org/doc/html/rfc9605](https://datatracker.ietf.org/doc/html/rfc9605)
- **Nguồn hỗ trợ / Triển khai**: [https://datatracker.ietf.org/wg/sframe/about/](https://datatracker.ietf.org/wg/sframe/about/), [https://www.rfc-editor.org/subjects/sframe/](https://www.rfc-editor.org/subjects/sframe/)
- **Tóm tắt cốt lõi**: RFC 9605 standardizes high-performance AEAD cipher suites (AES_128_GCM, AES_256_GCM, and CHACHA20_POLY1305) with 80-bit and 128-bit authentication tags tailored for low-latency media.
- **Phân tích kỹ thuật chuyên sâu & Kiến trúc Super-App**:
  [SPEC FACT] RFC 9605 §5 defines standardized SFrame cipher suites utilizing Authenticated Encryption with Associated Data (AEAD). The suite catalog includes 'AES_128_GCM_128' (mandatory to implement), 'AES_128_GCM_80' (truncated 80-bit tag for bandwidth-constrained audio), 'AES_256_GCM_128', and 'CHACHA20_POLY1305_128'. By using standard AEAD primitives, SFrame guarantees both confidentiality and strong cryptographic integrity for every transmitted media frame. The authenticated associated data (AAD) binds the SFrame header itself to the payload, preventing adversaries or malicious SFUs from modifying the KID or Counter fields without detection. [SUPERAPP ARCHITECTURE] Super-app mobile runtimes execute on a vast spectrum of hardware, from low-end ARM Cortex devices without hardware AES acceleration to flagship smartphones with dedicated cryptographic coprocessors. Super-app WebRTC engines negotiate CHACHA20_POLY1305 on budget devices to achieve maximum CPU efficiency and low thermal output, while activating AES_128_GCM on hardware-accelerated chips. Store security baseline standards mandate that all E2EE conference mini-apps implement RFC 9605 cipher suites.

### sframe_e2ee_068_04: Anti-Replay Verification and Cryptographic Sliding Window Governance
- **Chủ đề**: `sframe_anti_replay_sliding_window_protection` | **Nhóm chuyên mục**: `Security Architecture, Sandboxing & Vulnerability Management`
- **Mức bằng chứng**: `specification` | **Chuẩn tham chiếu**: IETF RFC 9605 §6 Cryptographic Processing & Anti-Replay
- **URL Chuẩn**: [https://datatracker.ietf.org/doc/html/rfc9605](https://datatracker.ietf.org/doc/html/rfc9605)
- **Nguồn hỗ trợ / Triển khai**: [https://datatracker.ietf.org/wg/sframe/about/](https://datatracker.ietf.org/wg/sframe/about/), [https://www.rfc-editor.org/subjects/sframe/](https://www.rfc-editor.org/subjects/sframe/)
- **Tóm tắt cốt lõi**: Receiving endpoints maintain an anti-replay sliding window tracking the SFrame Counter (CTR), rejecting replayed frames and out-of-order packets falling outside the window.
- **Phân tích kỹ thuật chuyên sâu & Kiến trúc Super-App**:
  [SPEC FACT] Under RFC 9605 §6, SFrame decapsulation enforces an anti-replay mechanism based on a sliding bitmask window. Because real-time UDP network delivery often results in packet reordering, the receiver maintains the highest observed counter (CTR_max) and a sliding window of recent counters (typically 64 to 128 frames). If an incoming frame has a CTR that has already been observed within the window or falls behind the trailing edge of the sliding window, the frame is immediately discarded without AEAD decryption. This prevents an active network adversary or compromised SFU from replaying recorded audio or video sequences (such as a replayed 'Yes, I authorize' voice snippet). [SUPERAPP ARCHITECTURE] Financial authorization, digital identity verification, and telemedicine mini-apps are vulnerable to video/audio replay spoofing if transport streams can be captured and reinjected. Super-app WebRTC transform pipelines implement RFC 9605 anti-replay verification at the receiver boundary. Mini-apps handling high-assurance video interactions must verify that the anti-replay window is active, rejecting packets failing replay checks and logging security violation telemetry to the super-app auditing service.

   - Các nút `<button>` sử dụng `commandfor` để điều khiển dialog hoặc popover bên trong thẻ `<form>` bắt buộc phải mang thuộc tính `type="button"` rõ ràng, loại bỏ nguy cơ submit form ngoài ý muốn.
   - Lệnh tùy biến bắt buộc phải tuân thủ cú pháp `--custom-name` (hai dấu gạch ngang phía trước).

   - Các mini-app cung cấp tính năng gọi thoại, gọi video bảo mật hoặc khám bệnh từ xa (telemedicine) bắt buộc phải mã hóa luồng media tại biên client bằng SFrame trước khi đưa vào kết nối WebRTC SFU.

   - Cửa sổ chống phát lại (anti-replay window) phải được kích hoạt và kiểm tra nghiêm ngặt đối với mọi khung hình nhận được.
